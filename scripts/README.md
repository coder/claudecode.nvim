# scripts

## Overview

`scripts/` holds developer and release tooling for claudecode.nvim. Nothing here is loaded by the plugin at runtime. The directory has five groups:

1. Shell libraries that speak JSON-RPC to the plugin's WebSocket server (`lib_claude.sh`, `lib_ws_persistent.sh`, `claude_shell_helpers.sh`). `lib_claude.sh` finds the server through its lock file. `lib_ws_persistent.sh` takes the URL and the token from its caller.
2. Interactive and probe clients built on those libraries (`claude_interactive.sh`, `mcp_test.sh`, `research_messages.sh`, `websocat.sh`, `test_neovim_websocket.sh`).
3. Test harnesses (`run_integration_tests_individually.sh`, `test_opendiff.lua`, `test_opendiff_simple.sh`, `manual_test_helper.lua`).
4. Standalone reproductions of GitHub issues (`repro_issue_*.lua`, `repro_issue_*.sh`). `repro_issue_70_probe.lua` matches that pattern, but it is a helper that `repro_issue_70.sh` runs.
5. Release tooling: a release-please wrapper that writes changelog entries with Communique (`release-please-runner.js`, `run-release-please.sh`, `package.json`, `package-lock.json`). `test-release-please-runner.js` holds the tests for `release-please-runner.js`. It also runs the pinned `communique` binary with the repo's `communique.toml` against a fake Anthropic API, to check that one release-notes submission fits the configured output budget.

CI runs four of these files: `.github/workflows/release-please.yaml` runs `./scripts/run-release-please.sh`, and `.github/workflows/test.yml` runs `./scripts/run_integration_tests_individually.sh` and `nvim --headless -u NONE -c "luafile scripts/repro_issue_238.lua" -c "cquit 2"` on Neovim stable and v0.8.0, and `npm --prefix scripts run test:release-please-runner` (which runs `test-release-please-runner.js`).

`mise.toml` provisions `websocat` and `jq` for the WebSocket scripts, and `communique` for the release tooling. It does not provide `agent-tty`, which `repro_issue_70.sh`, `repro_issue_218.sh`, and `repro_issue_277.sh` need. `repro_issue_277.sh` also needs `git` and `perl`, and `repro_issue_70.sh` needs a logged-in `claude` CLI [repro_issue_70.sh:MISSING dependency] [repro_issue_218.sh:agent-tty] [repro_issue_277.sh:MISSING dependency].

## Interface

### Shell libraries (source them)

- `lib_claude.sh` sets `CLAUDE_LOCKFILE_DIR` to `$CLAUDE_CONFIG_DIR/ide`, or to `$HOME/.claude/ide` when `CLAUDE_CONFIG_DIR` is unset or empty. It also exports `CLAUDE_LOG_DIR=mcp_test_logs` and `CLAUDE_WS_TIMEOUT=10` each time you source it, so set either variable after the `source` line [lib_claude.sh:CLAUDE_LOCKFILE_DIR, CLAUDE_LOG_DIR, CLAUDE_WS_TIMEOUT].
- `find_claude_lockfile` prints the port of the newest `*.lock` file by mtime and returns 1 when none exists. It reads the mtime with GNU `stat -c "%Y"`. BSD `stat` on macOS rejects that option, so there the function finds no lock file [lib_claude.sh:find_claude_lockfile].
- `get_claude_ws_url` prints `ws://localhost:PORT` [lib_claude.sh:get_claude_ws_url].
- `get_claude_auth_token PORT` reads `authToken` from `PORT.lock`, with `jq` or a `grep`/`sed` fallback [lib_claude.sh:get_claude_auth_token].
- `create_message`, `create_notification`, and `create_init_message` print JSON-RPC requests, notifications, and an `initialize` request (protocolVersion `2025-03-26`) [lib_claude.sh:create_message, create_notification, create_init_message].
- `send_claude_message MSG [WS_URL] [AUTH_TOKEN]` sends one message through `timeout` + `websocat`. It always returns 0. When `timeout` exits nonzero, it prints a JSON-RPC error with code `-32000` after any response it got [lib_claude.sh:send_claude_message]. Without an `AUTH_TOKEN` argument it reads the token from the newest lock file. With a token it puts `--header` before the URL. websocat 1.14.1, which `mise.toml` pins, takes the URL as a second header value and exits with `No URL specified`, so the call prints only the `-32000` error. `websocat --text` sends each line of the message as its own WebSocket message, and `create_message` prints multi-line JSON. The server answers each line that is not a whole JSON-RPC message with `-32700` [lib_claude.sh:send_claude_message, create_message].
- `list_claude_tools`, `get_current_selection`, `open_file PATH`, and `initialize_claude_session` wrap `tools/list`, `tools/call getCurrentSelection`, `tools/call openFile`, and the initialize handshake. `open_file` returns 0 even when the call fails [lib_claude.sh:list_claude_tools, get_current_selection, open_file, initialize_claude_session].
- `init_log_dir`, `log_message_and_response`, `claude_is_running`, `command_exists`, and `check_required_tools` are helpers for logging, liveness, and tool checks [lib_claude.sh:init_log_dir, log_message_and_response, claude_is_running, command_exists, check_required_tools].
- `lib_ws_persistent.sh` keeps a WebSocket open across calls. Functions: `ws_connect URL [CONN_ID] [AUTH_TOKEN]`, `ws_is_connected`, `ws_disconnect`, `ws_request JSON [CONN_ID] [TIMEOUT]`, `ws_notify`, `ws_rpc_request`, `ws_create_message`, `ws_format_json`, `ws_cleanup_all`, `ws_setup_trap`, `ws_start_listener CONN_ID CALLBACK [METHOD]`, and `ws_stop_listener` [lib_ws_persistent.sh:ws_connect, ws_request, ws_start_listener]. It uses `declare -A`, so it needs bash 4 or later [lib_ws_persistent.sh:WS_CONNECTIONS]. With a token, `ws_connect` puts `--header` before the URL, so websocat 1.14.1 exits with `No URL specified`, and `ws_connect` returns 1 [lib_ws_persistent.sh:ws_connect].
- `ws_rpc_request` special-cases `mcp.connect`: it sends a notification and returns a fake success [lib_ws_persistent.sh:ws_rpc_request].
- `claude_shell_helpers.sh` defines interactive shell commands: `claude_port`, `claude_ws_url`, `claude_running`, `claude_get_selection [-v|--verbose]`, `claude_open_file`, `claude_list_tools [-v|--verbose]`, `claude_send METHOD PARAMS [ID]`, `claude_interactive`, and `claude_help` [claude_shell_helpers.sh:claude_get_selection, claude_send, claude_help].
- `claude_shell_helpers.sh` sets `CLAUDE_LIB_DIR` from `$0`, or to `$HOME/.claude/bin` when `$0` is `-bash` or `-zsh`, and sources `lib_claude.sh` from there. When you source it from bash, `$0` names the shell, not this file, so `lib_claude.sh` must be in the directory that `CLAUDE_LIB_DIR` resolves to [claude_shell_helpers.sh:CLAUDE_LIB_DIR].
- `claude_get_selection` gets no response from the current plugin, because `send_claude_message` fails on websocat 1.14.1 (see above). So `claude_get_selection` prints `No text currently selected`, and `claude_get_selection -v` prints the `-32000` error [lib_claude.sh:send_claude_message]. Without `-v` or `--verbose` it also reads `.result.text`, while the server returns the selection as a JSON string in `result.content[0].text`. So a response with a selection also prints `No text currently selected` [claude_shell_helpers.sh:claude_get_selection]. `claude_open_file` prints `Opened:` whatever the server answers [claude_shell_helpers.sh:claude_open_file].

### WebSocket clients and probes

- `mcp_test.sh [-p|--port PORT] [-l|--logs DIR] [-t|--timeout SEC] [-c|--compact] [-h|--help] [tests]` runs the MCP tests `connect`, `toolslist`, `toolinvoke`, `methods`, and `selection`. The default is `all`, and a comma-separated list is accepted. The port defaults to `find_claude_lockfile` [mcp_test.sh:should_run_test, WEBSOCKET_PORT]. `-t` sets the per-request timeout (default 5 s). The selection test always listens for 10 s. `-h` exits 1, and the script skips an unknown test name without a message [mcp_test.sh:TIMEOUT, listen_duration, usage, should_run_test].
- In `mcp_test.sh`, against a server without an auth token, where the connect step works, `toolinvoke` and `methods` stop the whole run. `read -r` keeps the single quotes around each test case's params. `ws_format_json` (`jq -c`) rejects them, and `set -e` exits with jq's status: 5 with jq 1.7 and 1.8, and 4 with jq 1.6. So `all` never reaches `methods` or `selection` [mcp_test.sh:test_tool_invoke, test_methods] [lib_ws_persistent.sh:ws_format_json].
- `claude_interactive.sh` (no arguments) is a menu REPL: get selection, list tools, open file, custom JSON-RPC message, initialize, connection info, listen, reconnect, and exit [claude_interactive.sh:show_menu, handle_custom_message, handle_listen]. It exits 1 when the first `ws_connect` fails and exits 0 on the exit option [claude_interactive.sh:ws_connect].
- `research_messages.sh [-p|--port PORT] [-t|--timeout SEC] [-l|--log LOGFILE]` listens for TIMEOUT seconds (default 30), probes several method names, and prints counts of methods, ids, `selection_changed` notifications, and tool responses [research_messages.sh:send_test_message, TIMEOUT]. `-l` moves only the JSONL log. `claude_messages_pretty.txt` always goes to the current directory [research_messages.sh:PRETTY_LOG].
- In `research_messages.sh`, `grep -c` exits the script with 1 under `set -e` when the log holds no `selection_changed` notification, or no reply with id `2` or `3`. The probes go over separate one-shot `websocat -n1` connections whose replies never reach the log, so the script normally stops before its last count line [research_messages.sh:selection_changed_count, tool_responses, send_test_message].
- `websocat.sh` opens an interactive `websocat` session to `get_claude_ws_url` [websocat.sh:get_claude_ws_url].
- `test_neovim_websocket.sh [-t|--timeout SEC] [-l|--listen SEC] [-d|--log-dir DIR] [-h|--help] [all|connect|toolslist|selection]` starts Neovim with the plugin, waits for a new lock file, and runs connection, `tools/list`, and selection-listen tests [test_neovim_websocket.sh:usage, run_tests, find_newest_lockfile]. It must run from the repo root, because its init runs `set rtp+=.`. It starts a full-screen `nvim` in the same terminal, not a headless one [test_neovim_websocket.sh:NVIM_INIT_FILE, NVIM_PID].
- In `test_neovim_websocket.sh`, `((ELAPSED++))` returns status 1 when `ELAPSED` is 0, so `set -e` exits the script with 1 after the first one-second wait, unless the first check already found the new lock file. `((selection_count++))` ends the selection test the same way at its first notification [test_neovim_websocket.sh:ELAPSED, selection_count].

### Test harnesses

- `run_integration_tests_individually.sh` (no arguments) runs each `tests/integration/*_spec.lua` in its own headless Neovim under `timeout 30s`, skips `command_args_spec.lua`, and prints totals [run_integration_tests_individually.sh:run_test_file].
- `test_opendiff.lua` is a raw-socket Lua client that sends `tools/call openDiff` with an edited `README.md` [test_opendiff.lua:test_opendiff]. You run it with plain `lua` from the project root. It needs the `socket` (luasocket) and `json` Lua modules. `require("json")` raises an error when `json` is missing, so the `cjson` and `dkjson` fallbacks never run [test_opendiff.lua:json]. It exits 1 when setup or the handshake fails, and 0 otherwise [test_opendiff.lua:os.exit].
- `test_opendiff_simple.sh` sends the same `openDiff` call through `websocat` or `wscat` and reports exit 124 as "blocked" [test_opendiff_simple.sh:JSON_MESSAGE]. It must run from the project root, and it needs `jq` and `timeout`. It exits 0 even after it prints `❌ Connection failed` [test_opendiff_simple.sh:ABS_PATH, NEW_CONTENT].
- `manual_test_helper.lua` is run with `:luafile` in a Neovim that has the plugin on its `runtimepath`. It calls the `claudecode.tools.open_diff` handler in a coroutine and reports whether it yields [manual_test_helper.lua:test_opendiff_directly].

### Issue reproductions

The Lua repros run from the repository root with `nvim --headless -u NONE -l scripts/<file>`, which needs Neovim 0.9 or later. They prepend the repo root to `runtimepath` [repro_issue_208.lua:rtp:prepend]. `repro_issue_70_probe.lua` is the exception: it prepends `<repo_root>/lua` to `package.path` instead [repro_issue_70_probe.lua:package.path]. `repro_issue_238.lua` runs with the `:luafile` command in its entry below, which also works on Neovim 0.8.

- `repro_issue_70.sh` (#70) checks whether the `claude` CLI connects back to the plugin when an HTTP proxy has no localhost exclusion. It prints `PASS issue #70 reproduced` (exit 0) or `INCONCLUSIVE` (exit 1). It drives `repro_issue_70_probe.lua` [repro_issue_70.sh:run_scenario]. It needs `nvim`, `claude`, `agent-tty`, and `jq`, and exits 3 when one is missing [repro_issue_70.sh:MISSING dependency].
- `repro_issue_70_probe.lua <repo_root> <status_file> <stop_file> [wait_ms]` is a helper, not a standalone repro. `wait_ms` defaults to 120000 [repro_issue_70_probe.lua:wait_ms]. It starts the real server with `terminal.provider = "none"` and writes `phase`/`connected` JSON to the status file. Exit 0 means a connection was seen, 2 means none, and 1 means no port [repro_issue_70_probe.lua:write_status].
- `repro_issue_208.lua` (#208) checks for a leftover `[No Name]` tab or buffer after a diff resolves with `open_in_new_tab=true` and `provider=none`. Exit 0 means fixed, 1 means reproduced [repro_issue_208.lua:verdict].
- `repro_issue_218.sh [--no-render-markdown]` (#218) checks for a Neovim crash when a new-file markdown diff is accepted in a new tab with render-markdown.nvim. `NVIM_BIN` selects the binary. Exit 0 means the expected outcome happened. Exit 1 also covers a missing `agent-tty` or `nvim` and a failed `agent-tty` session. It uses `jq` but does not check for it [repro_issue_218.sh:WANT_RM, NVIM_BIN, SID].
- `repro_issue_231.lua` (#231) checks that a terminal-only layout does not fail with "No suitable editor window found". Exit 0 means fixed, 1 means reproduced [repro_issue_231.lua:verdict].
- `repro_issue_232.lua` (#232) checks for a `BufEnter` auto-insert autocmd on the terminal buffer. Env: `CLAUDECODE_PROVIDER=snacks|native`, `CLAUDECODE_AUTO_INSERT=true|false`. Exit 1 means reproduced, 0 means not reproduced or skipped, and 2 means a setup error [repro_issue_232.lua:reproduced]. `CLAUDECODE_PROVIDER` defaults to `snacks`. The script looks for snacks.nvim only at `~/.local/share/nvim/lazy/snacks.nvim` and `~/.local/share/*/lazy/snacks.nvim`, and prints `SKIP` (exit 0) when it cannot load it [repro_issue_232.lua:provider, candidates].
- `repro_issue_238.lua` (#238) checks that `:q` on the proposed window rejects the diff. CI runs it with `nvim --headless -u NONE -c "luafile scripts/repro_issue_238.lua" -c "cquit 2"`, which also works on Neovim 0.8. Exit 0 means fixed, 1 means reproduced, and 2 means the script raised an error before its verdict [repro_issue_238.lua:verdict]. It runs `open_in_new_tab=false`, `open_in_new_tab=true`, a split proposed window, and a new file. It finds the repo root with `:h:h` on its own path. `luafile` passes that path as you typed it, so run the CI command from the repo root, or pass an absolute path. Run from `scripts/` with a bare file name, it cannot load `claudecode.diff` and exits 2 [repro_issue_238.lua:run_scenario, run_multiwindow_scenario, run_newfile_scenario, repo_root].
- `repro_issue_238.sh --file PATH [--lock-dir DIR] [--out FILE] [--hold SEC] [--tab NAME]` (#238) is an external MCP client. It opens one `openDiff` and holds the socket while you run `:q` in Neovim. It prints a `RESULT:` line, but its exit code does not reflect the result [repro_issue_238.sh:RESULT]. `-h` prints the usage header. The lock directory is `CLAUDE_LOCKFILE_DIR`, else `$CLAUDE_CONFIG_DIR/ide`, else `$HOME/.claude/ide`, and `WEBSOCAT` overrides the binary. Exit 2 means a bad or missing argument, and exit 1 means a missing tool, lock file, or token. The proposed contents replace the text `line three` in `--file`, so a file without that text gets a diff with no change [repro_issue_238.sh:LOCK_DIR, WEBSOCAT, contents].
- `repro_issue_246.lua` (#246) checks that single-line and fast visual selections reach Claude. Exit 0 means all checks pass, 1 means a check failed [repro_issue_246.lua:check].
- `repro_issue_248.sh [-n|--num N] [--cleanup]` (#248) opens N diffs and disconnects without `close_tab`. It prints no verdict: run `:DiffState` in Neovim and read the counts [repro_issue_248.sh:NUM_DIFFS, CLEANUP]. `:DiffState` comes from the `fixtures/remote-diff` config. N is a cap: the script diffs the first N sorted `*.txt`, `*.lua`, and `*.md` files at the top level of `workspaceFolders[0]`. `-h` or `--help` prints the usage header, and an unknown argument exits 2. It exits 1 for a missing tool, a missing lock file, token, or workspace, or no file to diff. It exits 0 otherwise, because it ignores a `websocat` failure. It uses `mapfile`, so it needs bash 4 or later [repro_issue_248.sh:LOCK_DIR, FILES].
- `repro_issue_262.lua` (#262) checks that a setup error after `:tabnew` does not strand a tab. Exit 0 means fixed, 1 means reproduced [repro_issue_262.lua:verdict].
- `repro_issue_277.sh` (#277) runs three phases. Phases 1 and 3 check whether `closeAllDiffTabs` also closes diffview.nvim and user vimdiff windows. Phase 2 checks whether `openFile` runs `:edit` into a foreign diff window. `ISSUE277_ARTIFACTS` sets the artifact directory. The exit code covers all three phases: exit 0 means all three phases reproduced, 1 means a phase was not reproduced, 2 means a setup failure, and 3 means a missing tool [repro_issue_277.sh:PASS, FAIL, WEBSOCAT]. When `websocat --version` fails, the script searches `${MISE_DATA_DIR:-$HOME/.local/share/mise}/installs/websocat` for a working `websocat` binary. It exits 3 when that search finds no working binary [repro_issue_277.sh:WEBSOCAT].
- `repro_issue_283.lua` (#283) checks the port probe. `REPRO283_MODE` selects `mechanism` (the default, also used for an unknown value), `port`, or `serve`. Serve mode reads `REPRO283_LABEL` and `REPRO283_WAIT_MS` (default 6000) [repro_issue_283.lua:mode, label, wait_ms]. Mechanism mode rebuilds the probe with raw `vim.loop` handles and calls no plugin code. Its exit 1 means libuv accepted a bind on a busy port and failed later at `listen`. That result does not change when the plugin is fixed [repro_issue_283.lua:reproduced].
- `repro_issue_283.sh` (#283) runs `repro_issue_283.lua` in all three modes. `NVIM` overrides the binary, and the script exits 2 when it cannot find it. Exit 1 means all three parts reproduced. Exit 0 means "not fully reproduced", not "pass" [repro_issue_283.sh:VERDICT]. Part 3 looks for the text `Failed to listen on port .*EADDRINUSE`. The current `create_server` moves on to the next port and never returns that text, so on current code the script exits 0 [repro_issue_283.sh:E2E] [lua/claudecode/server/tcp.lua:create_server].
- `repro_issue_285.lua` (#285) checks that a path with a `$post` segment is accepted by `:ClaudeCodeAdd` and the `openFile` handler, and that `:ClaudeCodeAdd %` still works. Exit 0 means fixed, 1 means reproduced or a regression [repro_issue_285.lua:verdict].
- `repro_issue_289.lua` (#289) checks that `ClaudeCodeSend` does not treat a Lua buffer as a file-tree buffer because its path contains `neo-tree`. It tests a `_neo-tree_.lua` path against a control path. It does not test an `NvimTree` path. Exit 1 means reproduced [repro_issue_289.lua:AFFECTED, affected_misrouted].

### Release tooling

- `run-release-please.sh [args]` changes to the repo root and runs `node release-please-runner.js`. It uses `scripts/node_modules/release-please` when present, else the `release-please` on `PATH` through `NODE_PATH`. When it finds neither, it exits 1 with no message [run-release-please.sh:release_please_bin].
- `node release-please-runner.js [--dry-run]` registers Communique-generated changelog notes and the `simple` release type, then creates releases and release PRs. Without `--dry-run` it prints `release-please: releases=[...] prs=[...]`. With `--dry-run` it prints JSON with `releases` and `pullRequests` (including `changelogPreview`) and writes nothing to GitHub. `--dry-run` still needs `GITHUB_TOKEN` and still reads from the GitHub API. Any error sets exit code 1 [release-please-runner.js:main].
- `buildCommuniqueArgs` builds `communique generate HEAD [PREVIOUS_TAG] --concise --repo OWNER/REPO --output <tmp>/notes.md [--model COMMUNIQUE_MODEL]` [release-please-runner.js:buildCommuniqueArgs].
- Environment for `release-please-runner.js`: `GITHUB_TOKEN` and `GITHUB_REPOSITORY` (required), `RELEASE_PLEASE_TARGET_BRANCH`, `GITHUB_OUTPUT`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `COMMUNIQUE_MODEL`, and `PRETTIER_BIN` [release-please-runner.js:requireEnv, assertLlmCredentials, resolvePrettierBin].
- `release-please-runner.js` exports `CommuniqueSimpleStrategy`, `UnreleasedAwareChangelog`, `assertLlmCredentials`, `buildCommuniqueArgs`, `createCommuniqueChangelogNotes`, `findLineOutsideFences`, `formatChangelogMarkdown`, `formatChangelogSection`, `formatPullRequestOutputs`, `formatReleaseOutputs`, `normalizeCommuniqueBody`, `resolvePrettierBin`, `releasePleaseNotesAreEmpty`, and `todayIsoDate` [release-please-runner.js:module.exports].
- GitHub Actions outputs: `releases_created`, `release_tags`, `prs_created`, `pr_branches`, and `pr_metadata` [release-please-runner.js:formatReleaseOutputs, formatPullRequestOutputs].
- `package.json` is the private package `claudecode.nvim-release-tools`. It pins `prettier` 3.8.4 and `release-please` 17.9.0 and defines the `test:release-please-runner` script [package.json:scripts]. `package-lock.json` locks the full dependency tree of `package.json` [package-lock.json:packages]. Both CI workflows install from it with `npm ci --prefix scripts` [.github/workflows/test.yml:npm ci] [.github/workflows/release-please.yaml:npm ci].
- `test-release-please-runner.js` takes no arguments and prints nothing on success. `npm run` prints only its own two-line header. It needs `git`, `prettier`, the `release-please` package, a real `communique` binary on `PATH` (for example under `mise exec --`), and the repo's `communique.toml`. It runs `communique` in a temp directory outside the repo. There a mise shim for the `communique` that the repo's `mise.toml` pins prints `communique is not a valid shim`, and the test exits 1. Its Communique check asserts that one release-notes submission is between 4096 and 8192 tokens and gets through in one request [test-release-please-runner.js:testCommuniqueConfigFitsReleaseNotes].

## Invariants

- Most clients find the server port from the lock file name (`PORT.lock`) in a lock directory. `mcp_test.sh` and `research_messages.sh` skip that lookup when you pass `-p`. `send_claude_message`, the first `ws_connect` in `claude_interactive.sh`, `repro_issue_238.sh`, and `repro_issue_248.sh` send the lock file's `authToken` in the `x-claude-code-ide-authorization` header. `repro_issue_277.sh` sends the same header, but reads the port and the token from the plugin state through nvim RPC [lib_claude.sh:get_claude_auth_token, send_claude_message] [lib_ws_persistent.sh:ws_connect] [repro_issue_238.sh:TOKEN] [repro_issue_248.sh:TOKEN]. `repro_issue_238.sh`, `repro_issue_248.sh`, and `repro_issue_277.sh` put the URL before `--header`, which websocat 1.14.1 accepts. `send_claude_message` and `ws_connect` put it after, so on websocat 1.14.1 they exit with `No URL specified` before they connect [repro_issue_238.sh:WEBSOCAT] [repro_issue_277.sh:WEBSOCAT] [lib_claude.sh:send_claude_message] [lib_ws_persistent.sh:ws_connect]. `mcp_test.sh`, `test_neovim_websocket.sh`, `research_messages.sh`, `websocat.sh`, `test_opendiff.lua`, and `test_opendiff_simple.sh` send no token. The plugin server rejects their upgrade request when it has an auth token, which `start` always sets, so these six clients cannot talk to the current plugin. `mcp_test.sh` exits 1 at its connect step [mcp_test.sh:ws_connect, test_connection] [websocat.sh:websocat] [lua/claudecode/server/handshake.lua:validate_upgrade_request].
- `lib_claude.sh` checks only `websocat` and `jq`. Sourcing it runs `check_required_tools`, which returns 1 when one is missing but does not call `exit`. A caller that sourced it under `set -e` (`mcp_test.sh`, `research_messages.sh`, `test_neovim_websocket.sh`) therefore exits. `send_claude_message` also needs `timeout` [lib_claude.sh:check_required_tools, send_claude_message].
- `send_claude_message` builds a single-quoted `bash -c` string, so a single quote in the message or token breaks the command [lib_claude.sh:send_claude_message].
- `lib_ws_persistent.sh` assumes single-line compact JSON. `ws_request` needs a non-empty `.id`, and `ws_start_listener` matches the exact text `"method":"NAME"` [lib_ws_persistent.sh:ws_request, ws_start_listener].
- `ws_request` reads only response bytes written after the request starts. On timeout it prints the last received line when any bytes arrived, else a JSON-RPC error with code `-32000`. It still returns 0 [lib_ws_persistent.sh:ws_request].
- `ws_connect` disconnects an existing connection with the same `CONN_ID` first, and returns 1 unless the process is alive after 0.5 s [lib_ws_persistent.sh:ws_connect].

## Side Effects

- Sourcing `lib_ws_persistent.sh` creates `${TMPDIR:-/tmp}/ws_logs`. `ws_connect` writes `pid`, `log.txt`, `request.json`, and `response.json` under `ws_logs/CONN_ID/` and starts a background `tail -f | websocat | tee` pipeline [lib_ws_persistent.sh:WS_LOG_DIR, ws_connect]. `ws_request` appends every request to `ws_logs/CONN_ID/debug.log`, which nothing truncates. No function deletes `ws_logs/CONN_ID/` [lib_ws_persistent.sh:ws_request].
- `ws_disconnect` sends SIGTERM to the saved PID only. That PID is `$!` of the pipeline, which is the `tee` process, not `tail -f` or `websocat`. After each `mcp_test.sh` run, also one whose connect step fails, its `tail -f` and the subshell that waits for the pipeline keep running. After a `set -e` exit in `toolinvoke`, `methods`, or `all`, its `websocat` keeps running too [mcp_test.sh:ws_connect]. It sends SIGKILL only when the SIGTERM send fails, not when the process ignores SIGTERM. `ws_setup_trap` runs `ws_cleanup_all` on EXIT, INT, and TERM, and sourcing the library installs that trap. The trap does not call `exit`, so after Ctrl+C the caller closes its connections and keeps running [lib_ws_persistent.sh:ws_connect, ws_disconnect, ws_setup_trap].
- `ws_start_listener` starts a background polling loop (0.5 s) and writes `listener.pid` [lib_ws_persistent.sh:ws_start_listener]. The loop has no exit condition. Only `ws_stop_listener` kills it, and it reads `listener.pid`, which each `ws_start_listener` call overwrites. `ws_disconnect`, `ws_cleanup_all`, and the trap leave listeners running. `mcp_test.sh` starts up to five listeners and stops at most the last one, so the others keep polling after the script exits [lib_ws_persistent.sh:ws_stop_listener, ws_cleanup_all] [mcp_test.sh:ws_start_listener, ws_stop_listener].
- CAUTION: Do not run the token-sending clients on a shared machine, and do not share the output of `claude_interactive.sh` option 6. The scripts pass the auth token on the `websocat` command line (`--header`), where other users can read it with `ps`. Option 6 prints the whole lock file, including `authToken` [lib_claude.sh:send_claude_message] [lib_ws_persistent.sh:ws_connect] [repro_issue_238.sh:WEBSOCAT] [repro_issue_248.sh:TOKEN] [repro_issue_277.sh:TOKEN] [claude_interactive.sh:handle_connection_info].
- Log directories are created relative to the current directory: `mcp_test_logs` [mcp_test.sh:LOG_DIR], `mcp_interactive_logs` [claude_interactive.sh:CLAUDE_LOG_DIR], `test_neovim_ws_logs` [test_neovim_websocket.sh:LOG_DIR], and `claude_messages.jsonl` / `claude_messages_pretty.txt` [research_messages.sh:LOG_FILE]. Each run truncates its log files, except `claude_interactive.sh`, which only creates its log directory. `claude_interactive.sh` keeps its connection files in `${TMPDIR:-/tmp}/ws_logs/claude_interactive/` [claude_interactive.sh:CONN_ID].
- Sourcing `claude_shell_helpers.sh` sets `CLAUDE_LOG_DIR=$HOME/.claude/logs` and creates that directory [claude_shell_helpers.sh:CLAUDE_LOG_DIR].
