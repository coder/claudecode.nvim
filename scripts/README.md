# scripts

## Overview

`scripts/` holds developer and release tooling for claudecode.nvim. Nothing here is loaded by the plugin at runtime. The directory has four groups:

1. Test harnesses (`run_integration_tests_individually.sh`, `manual_test_helper.lua`) and `coverage-summary.sh`, which turns the luacov report into the CI coverage summary.
2. Standalone reproductions of GitHub issues (`repro_issue_*.lua`, `repro_issue_*.sh`). `repro_issue_70_probe.lua` matches that pattern, but it is a helper that `repro_issue_70.sh` runs.
3. Release tooling: a release-please wrapper that writes changelog entries with Communique (`release-please-runner.js`, `run-release-please.sh`, `package.json`, `package-lock.json`). `test-release-please-runner.js` holds the tests for `release-please-runner.js`. Among them, a differential test compares fence tracking and heading demotion with commonmark.js on generated documents, and a property test runs the Unreleased update on generated drafts and checks that every older release stays a top-level heading. It also runs the pinned `communique` binary with the repo's `communique.toml` against a fake Anthropic API, to check that one release-notes submission fits the configured output budget.
4. TLA+ model-check tooling in `tla/`: `check-lib.sh`, the harness that every `.agents/skills/verify-*/check.sh` sources, and `test-check-lib.sh`, its tests.

CI runs seven of these files. The `release-please` job of `.github/workflows/release-please.yaml` runs `./scripts/run-release-please.sh`. `.github/workflows/test.yml` runs the other six in three jobs. The `unit-tests` job runs `npm --prefix scripts run test:release-please-runner` (which runs `test-release-please-runner.js`) before the unit tests, and `scripts/coverage-summary.sh luacov.report.out "$PWD"` after them. The `integration-tests` job runs on Neovim stable and v0.8.0. It runs `./scripts/run_integration_tests_individually.sh` twice (the second time with a `TMPDIR` that holds a space and a `%`), then `nvim --headless -u NONE -c "luafile scripts/repro_issue_238.lua" -c "cquit 2"`, then `scripts/manual_test_helper.lua` by absolute path from a directory outside the repo. The `covered-lock` job runs every `.agents/skills/verify-*/check.sh`, and each of those sources `scripts/tla/check-lib.sh`. Then it runs `scripts/tla/test-check-lib.sh`. The `Required` job needs only `unit-tests` and `integration-tests` [.github/workflows/test.yml:unit-tests, integration-tests, covered-lock, required].

`mise.toml` provisions `websocat` for `repro_issue_238.sh`, `repro_issue_248.sh`, and `repro_issue_277.sh`, `jq` for the repro scripts that parse JSON, and `communique` for the release tooling. It does not provide `agent-tty`, which `repro_issue_70.sh`, `repro_issue_218.sh`, and `repro_issue_277.sh` need. `repro_issue_277.sh` also needs `git` and `perl`, and `repro_issue_70.sh` needs the `claude` CLI [repro_issue_70.sh:MISSING dependency] [repro_issue_218.sh:agent-tty] [repro_issue_277.sh:MISSING dependency].

For a manual WebSocket check, create an empty out file, then run `mise exec -- node .agents/skills/verify-claudecode-nvim/scripts/ws-client.mjs <lock file> <out file> <in file>` from the repo root: it connects with the lock file's token, which it reads from the file so the token never appears in argv, sends each line you append to the out file, and appends each message it receives to the in file. The client opens the out file with `openSync(..., "r")`, so a missing out file fails with `ENOENT` [.agents/skills/verify-claudecode-nvim/scripts/ws-client.mjs:authToken, openSync].

## Interface

### Test harnesses

- `run_integration_tests_individually.sh` (no arguments) runs each `tests/integration/*_spec.lua` in its own headless Neovim under `timeout -k 5s 40s` (plenary's `test_file` ends a file at 50 s on its own, without a `TIMEOUT:` line, so the limit plus the kill grace stays under 50 s), and prints totals. For each file it sets `VIMINIT` and `CLAUDECODE_MINIMAL_INIT` (the absolute path of `tests/minimal_init.lua`) so the Neovim that plenary starts runs that file, and gives the Neovim it starts and the one plenary starts for the file one pair of `XDG_STATE_HOME` and `XDG_CONFIG_HOME` temp folders to share (the Neovim it starts takes `-i NONE`, so only one of them writes ShaDa) [run_integration_tests_individually.sh:run_test_file].
- `manual_test_helper.lua` is run with `:luafile` in a Neovim that has the plugin on its `runtimepath`. It calls the `claudecode.tools.open_diff` handler in a coroutine and reports whether it yields [manual_test_helper.lua:test_opendiff_directly]. CI fails unless it opens the repo's `README.md` and the handler yields [.github/workflows/test.yml:Manual openDiff helper works outside the repo].
- `manual_test_helper.lua` calls the handler itself, not through the server's `tools/call` path, so no response sender for its coroutine is stored in `_G.claude_deferred_responses`. When the diff resolves after the handler yielded (an accept, a reject, or a Neovim exit with the diff still open), the resolution callback resumes the coroutine and the helper prints `openDiff completed with result:`. Then `diff.lua` logs `[ClaudeCode] [diff] [ERROR] No global response sender found for coroutine: thread: 0x...`. For the helper this line is expected and harmless: no client waits for that reply, and the exit code stays 0. The CI step logs it too, because `qa!` rejects the open diff [manual_test_helper.lua:test_opendiff_directly] [diff.lua:open_diff_blocking] [server/init.lua:_setup_deferred_response].
- `coverage-summary.sh <luacov.report.out> <checkout folder>` prints a Markdown summary of the report's Summary table: the Total row as the overall figure, then one row per file with the checkout folder stripped and a mark per threshold (90% and above, 70% and above, below 70%). It exits 0 when it prints the summary, 1 when the report has no file row, no Total row or a repeated path, 2 when the report cannot be read, and 64 for the wrong number of arguments. `tests/unit/coverage_summary_spec.lua` runs it on small reports [coverage-summary.sh:emoji].

### TLA+ model checks

- `tla/check-lib.sh` is sourced by each `.agents/skills/verify-*/check.sh`. The check sets `here`, `SKILL` and `MODEL`, then calls `tla_init "$@"`, which parses the options and moves to the repo root. Only then does it call `covered_block`. It sets `COVERED`, `SITE_RE`, `FACTS`, `RULES`, `LIVE`, `EXPECT`, `CONSTRAINT` and `tla_constants`, sets its facts, and calls `tla_main "$@"` last. The header of the file lists the contract [check-lib.sh:tla_init, tla_main].
- The options are `--mutants`, `--keep`, `--record` and `--hash-only`. The exit codes are 0 (pass), 1 (a rule broke), 2 (tool or script error, or a broken `TypeOK`) and 3 (the covered code changed since `covered.lock` was recorded). When more than one applies, 2 wins over 1, and 1 wins over 3. A usage error, a bad `check.sh` setup or a failed jar fetch exits 2 before any TLC run, even when the lock is stale. A plain run exits 2 at once on a broken `TypeOK` or a TLC error, and exits 1 after its runs when a rule broke. With `--mutants`, a TLC error or a mutant that breaks the wrong rule gives 2, and a guard that no rule catches or a rule that never breaks gives 1. Both modes exit 3 only when nothing broke and the lock is stale, so a stale lock plus a broken rule exits 1. `--hash-only` runs no TLC and exits 0 or 3. `--record` writes the lock and exits 0, stale or not. The lib turns on `set -euo pipefail`. In the code of a `check.sh`, a failed command exits with that command's status (often 1, the code for a broken rule), and an unset variable exits 1. A script that sources the lib and ends without `tla_main` exits 2 when it would exit 0, and keeps any other exit code [check-lib.sh:tla_parse_args, tla_lock, tla_check, tla_mutants, tla_on_exit].
- `tla/test-check-lib.sh [PATH_TO_CHECK_LIB]` builds a toy skill on the lib in a scratch git repo and runs real TLC on a one-variable model. It prints one line per case and a `COUNT cases=N failed=N skipped=N` line, and exits 1 when a case fails [test-check-lib.sh:expect].

### Issue reproductions

The Lua repros run from the repository root with `nvim --headless -u NONE -l scripts/<file>`, which needs Neovim 0.9 or later. Each of them except `repro_issue_70_probe.lua` takes the repo root from its own path (two folders up) and puts it on `runtimepath`. So an absolute path works from any directory, but a bare file name run from `scripts/` fails with `module 'claudecode.diff' not found` (or another `claudecode` module). `repro_issue_70_probe.lua` takes the repo root as its first argument instead. Under `nvim -l`, an uncaught Lua error prints an `E5113` error and exits 1, the code that most repros use for "reproduced", so read the output to tell them apart. A script's own `cquit N` or `os.exit(N)` exits N, and a script that ends without either exits 0. `repro_issue_238.lua` also runs with the `:luafile` command in its entry below, which works on Neovim 0.8. In that form an uncaught error falls through to the second `-c` and exits 2, and so does a script that ends without `cquit` [repro_issue_208.lua:repo_root] [repro_issue_70_probe.lua:package.path].

- `repro_issue_70.sh` (#70) checks whether the `claude` CLI connects back to the plugin when an HTTP proxy has no localhost exclusion. It prints `PASS issue #70 reproduced` (exit 0) or `INCONCLUSIVE` (exit 1). It drives `repro_issue_70_probe.lua` [repro_issue_70.sh:start_probe]. It needs `nvim`, `claude`, `agent-tty`, and `jq`, and exits 3 when one is missing [repro_issue_70.sh:MISSING dependency].
- `repro_issue_70_probe.lua <repo_root> <status_file> <stop_file> [wait_ms]` is a helper that `repro_issue_70.sh` runs, not a standalone repro. It starts the real server with `terminal.provider = "none"` and writes its state to the status file [repro_issue_70_probe.lua:write_status].
- `repro_issue_208.lua` (#208) checks for a leftover `[No Name]` tab or buffer after a diff resolves with `open_in_new_tab=true` and `provider=none`. Exit 0 means fixed, 1 means reproduced [repro_issue_208.lua:verdict].
- `repro_issue_218.sh [--no-render-markdown]` (#218) checks for a Neovim crash when a new-file markdown diff is accepted in a new tab with render-markdown.nvim. `NVIM_BIN` selects the binary. Exit 0 means the expected outcome happened [repro_issue_218.sh:WANT_RM, NVIM_BIN].
- `repro_issue_231.lua` (#231) checks that a terminal-only layout does not fail with "No suitable editor window found". Exit 0 means fixed, 1 means reproduced [repro_issue_231.lua:verdict].
- `repro_issue_232.lua` (#232) checks for a `BufEnter` auto-insert autocmd on the terminal buffer. Env: `CLAUDECODE_PROVIDER=snacks|native` (default `snacks`) and `CLAUDECODE_AUTO_INSERT=true|false`. Exit 1 means reproduced, 0 means not reproduced or skipped, and 2 means a setup error [repro_issue_232.lua:reproduced]. The `snacks` provider needs snacks.nvim in `~/.local/share/nvim/lazy/snacks.nvim` or `~/.local/share/*/lazy/snacks.nvim`. When the script cannot load it, it prints `SKIP` and exits 0 [repro_issue_232.lua:provider, candidates].
- `repro_issue_238.lua` (#238) checks that `:q` on the proposed window rejects the diff. CI runs it with `nvim --headless -u NONE -c "luafile scripts/repro_issue_238.lua" -c "cquit 2"`, which also works on Neovim 0.8. Exit 0 means fixed and 1 means reproduced. When the script raises an error before its verdict, the exit code depends on the form: the CI form exits 2, but `nvim -l` exits 1, the same code as reproduced, so read the output to tell them apart [repro_issue_238.lua:verdict]. It finds the repo root from its own path, so run it from the repo root or pass an absolute path. Run from `scripts/` with a bare file name, it fails with a module-not-found error, which exits 2 in the CI form and 1 under `nvim -l` [repro_issue_238.lua:repo_root].
- `repro_issue_238.sh --file PATH [--lock-dir DIR] [--out FILE] [--hold SEC] [--tab NAME]` (#238) is an external MCP client. It opens one `openDiff` and holds the socket while you run `:q` in Neovim. It prints a `RESULT:` line, but its exit code does not reflect the result [repro_issue_238.sh:RESULT]. The lock directory is `CLAUDE_LOCKFILE_DIR`, else `$CLAUDE_CONFIG_DIR/ide`, else `$HOME/.claude/ide`, and `WEBSOCAT` overrides the binary. Exit 2 means a missing `--file`, an unknown option, or a `--file` that names no file. Exit 1 means a missing tool, lock file, or token. The proposed contents replace the text `line three` in `--file`, so a file without that text gets a diff with no change [repro_issue_238.sh:LOCK_DIR, WEBSOCAT, contents].
- `repro_issue_246.lua` (#246) checks that single-line and fast visual selections reach Claude. Exit 0 means all checks pass, 1 means a check failed [repro_issue_246.lua:check].
- `repro_issue_248.sh [-n|--num N] [--cleanup]` (#248) opens N diffs and disconnects without `close_tab`. It prints no verdict: run `:DiffState` in Neovim and read the counts [repro_issue_248.sh:NUM_DIFFS, CLEANUP]. `:DiffState` comes from the `fixtures/remote-diff` config. N caps how many `*.txt`, `*.lua`, and `*.md` files at the top level of `workspaceFolders[0]` it diffs. An unknown option exits 2. A missing tool, a missing lock file, token, or workspace, or no file to diff exits 1. It ignores a `websocat` failure, so exit 0 does not prove that the diffs opened. It uses `mapfile`, so it needs bash 4 or later [repro_issue_248.sh:LOCK_DIR, FILES].
- `repro_issue_262.lua` (#262) checks that a setup error after `:tabnew` does not strand a tab. Exit 0 means fixed, 1 means reproduced [repro_issue_262.lua:verdict].
- `repro_issue_277.sh` (#277) runs three phases. Phases 1 and 3 check whether `closeAllDiffTabs` also closes diffview.nvim and user vimdiff windows. Phase 2 checks whether `openFile` runs `:edit` into a foreign diff window. `ISSUE277_ARTIFACTS` sets the artifact directory. Exit 0 means all three phases reproduced, 1 means a phase was not reproduced, 2 means a setup failure, and 3 means a missing tool [repro_issue_277.sh:PASS, FAIL, WEBSOCAT]. When the `websocat` on `PATH` does not run, the script falls back to one under `${MISE_DATA_DIR:-$HOME/.local/share/mise}/installs/websocat`, and exits 3 when that fallback is missing or does not run [repro_issue_277.sh:WEBSOCAT].
- `repro_issue_283.lua` (#283) checks the port probe. `REPRO283_MODE` selects `mechanism` (the default), `port`, or `serve`. Serve mode reads `REPRO283_LABEL` and `REPRO283_WAIT_MS` (default 6000) [repro_issue_283.lua:mode, label, wait_ms]. Mechanism mode uses raw `vim.loop` handles and calls no plugin function. Its exit 1 means libuv accepted a bind on a busy port and failed later at `listen`, and that result does not change when the plugin is fixed [repro_issue_283.lua:reproduced].
- `repro_issue_283.sh` (#283) runs `repro_issue_283.lua` in all three modes. `NVIM` overrides the binary, and the script exits 2 when it cannot find it. Exit 1 means all three parts reproduced, and exit 0 means "not fully reproduced", not "pass" [repro_issue_283.sh:VERDICT].
- `repro_issue_285.lua` (#285) checks that a path with a `$post` segment is accepted by `:ClaudeCodeAdd` and the `openFile` handler, and that `:ClaudeCodeAdd %` still works. Exit 0 means fixed, 1 means reproduced or a regression [repro_issue_285.lua:verdict].
- `repro_issue_289.lua` (#289) checks that `ClaudeCodeSend` does not treat a Lua buffer as a file-tree buffer because its path contains `neo-tree`. Exit 1 means reproduced [repro_issue_289.lua:AFFECTED, affected_misrouted].

### Release tooling

- `run-release-please.sh [args]` changes to the repo root and runs `node release-please-runner.js` with the same arguments. It uses `scripts/node_modules/release-please` when present, else the `release-please` on `PATH` through `NODE_PATH`, and `commonmark` must be on that path too or the runner fails at start-up, before any GitHub call. It prints nothing itself. When neither exists, `command -v release-please` fails under `set -e`, and the script exits 1 with no message [run-release-please.sh:release_please_bin].
- `node release-please-runner.js [--dry-run]` registers Communique-generated changelog notes and the `simple` release type, then creates releases and release PRs. release-please's own logger writes info and debug lines (`✔`, `❯`) to stdout and warnings and errors (`⚠`, `✖`) to stderr. Without `--dry-run`, the runner writes `releases_created` and `release_tags` after it creates releases, then `prs_created`, `pr_branches` and `pr_metadata` after it creates PRs, as `key=value` lines. It appends them to the file that `GITHUB_OUTPUT` names, or prints them to stdout when `GITHUB_OUTPUT` is unset or empty. Last, it prints `release-please: releases=[...] prs=[...]` to stdout. With `--dry-run`, it prints JSON with `releases` and `pullRequests` (including `changelogPreview`) to stdout after the log lines, so stdout is not pure JSON. `--dry-run` writes nothing to GitHub and no `GITHUB_OUTPUT` line. It still needs `GITHUB_TOKEN`, still reads from the GitHub API, and still runs Communique, an LLM call that needs an API key, for each release PR whose default notes have more than one line. The runner copies Communique's stderr to its own stderr, and Prettier's stderr reaches its stderr directly. Communique writes `notes.md` in a `communique-notes-*` folder under the OS temp dir, and the runner removes that folder. Any error prints the error with its stack to stderr and sets exit code 1 [release-please-runner.js:main, writeGithubOutputs, runCommuniqueBinary, createCommuniqueChangelogNotes, formatChangelogMarkdown].
- Environment for `release-please-runner.js`: `GITHUB_TOKEN` and `GITHUB_REPOSITORY` (required), `RELEASE_PLEASE_TARGET_BRANCH`, `GITHUB_OUTPUT`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `COMMUNIQUE_MODEL`, and `PRETTIER_BIN` [release-please-runner.js:requireEnv, assertLlmCredentials, resolvePrettierBin].
- GitHub Actions outputs: `releases_created`, `release_tags`, `prs_created`, `pr_branches`, and `pr_metadata` [release-please-runner.js:formatReleaseOutputs, formatPullRequestOutputs].
- `package.json` is the private package `claudecode.nvim-release-tools`. It pins `prettier` 3.8.4, `release-please` 17.9.0, and `commonmark` 0.31.2 (used by the runner and its tests) and defines the `test:release-please-runner` script [package.json:scripts]. `package-lock.json` locks the full dependency tree of `package.json` [package-lock.json:packages]. Both CI workflows install from it with `npm ci --prefix scripts` [.github/workflows/test.yml:npm ci] [.github/workflows/release-please.yaml:npm ci].
- `test-release-please-runner.js` takes no arguments and prints nothing on success. It needs `git`, `prettier`, the `release-please` package, a real `communique` binary on `PATH` (for example under `mise exec --`), and the repo's `communique.toml`. It runs `communique` in a temp directory outside the repo, so a mise shim for `communique` fails there with `communique is not a valid shim` and the test exits 1. Its Communique check asserts that `communique` gets one release-notes submission, which is larger than its default 4096-token output budget, through in one request [test-release-please-runner.js:testCommuniqueConfigFitsReleaseNotes]. `testUnreleasedDraftEnd` runs that `communique` on a table of small changelogs, a few at a time, against a fake Anthropic API, and checks that `findCommuniqueDraft` finds the draft that the binary sends to the model, so a new Communique version that reads a draft differently fails it. The tests of the Unreleased draft read `scripts/fixtures/changelog-released.md`, a frozen copy of the released sections of `CHANGELOG.md` (0.4.0 and older), and `scripts/fixtures/changelog-drafts.json`, the head, draft and older part of each of the 20 states of `CHANGELOG.md` that have an Unreleased heading, and never read `CHANGELOG.md` itself [test-release-please-runner.js:testUnreleasedDraftFenceGuard, testUnreleasedDraftStructure, testUnreleasedDraftEnd].

## Invariants

- `repro_issue_238.sh` and `repro_issue_248.sh` find the server port from the lock file name (`PORT.lock`) in a lock directory, and send the lock file's `authToken` in the `x-claude-code-ide-authorization` header. `repro_issue_277.sh` sends the same header, but reads the port and the token from the plugin state through nvim RPC [repro_issue_238.sh:TOKEN] [repro_issue_248.sh:TOKEN] [repro_issue_277.sh:TOKEN]. All three put the URL before `--header`, because websocat 1.14.1 reads the URL as a header value when `--header` comes first and exits with `No URL specified` [repro_issue_238.sh:WEBSOCAT] [repro_issue_277.sh:WEBSOCAT].
- `run_integration_tests_individually.sh` must run from the repo root: `-u tests/minimal_init.lua` and `CLAUDECODE_MINIMAL_INIT` (`$PWD/tests/minimal_init.lua`) name the file from the working folder. It reads only the three summary lines that plenary prints, `Success:`, `Failed :` and `Errors :`, and none of the `Success ||` or `Fail ||` rows. A line counts only when it starts with its word, after the color codes are removed, and the last such line of each word wins. It adds a file to `FAILED_FILES` when the summary counts a failure or an error, when nvim exits nonzero, or when the output has no plenary summary: one of the three lines is missing, or its count is not `0` or 1 to 9 of the ASCII digits `0` to `9` with no leading zero, in every locale. Plenary prints the summary only after it ran the whole file, so a missing summary means nvim stopped early, for example in a Lua crash that exits 0. Plenary also prints none for a file without a top-level `describe`. The script prints `FAILED: <file>: no plenary summary (nvim exit N)` for such a file and counts it as one error. `Total Success`, `Total Failed` and `Total Errors` are the sums of the summary counts. It counts a timeout (exit 124), a SIGKILL from `timeout -k 5s` (exit 137) and SIGTERM (exit 143) too, even when every spec passed and plenary printed its summary, because nvim did not exit in time. It prints a `TIMEOUT:` line for each such file and then kills every process left in the process group of `timeout`, since a spec that spins in Lua ignores SIGTERM and leaves its nvim running. It exits 1 when `FAILED_FILES` is non-empty or the parsed failure or error totals are non-zero, else 0 [run_integration_tests_individually.sh:FAILED_FILES, TOTAL_FAILED].
- `repro_issue_238.sh` and `repro_issue_248.sh` take the first lock file found, not the newest [repro_issue_238.sh:LOCK_FILE] [repro_issue_248.sh:LOCK_FILE].
- `repro_issue_238.sh` and `repro_issue_248.sh` read `CLAUDE_LOCKFILE_DIR` from the environment. `repro_issue_248.sh` falls back to `$HOME/.claude/ide` and ignores `CLAUDE_CONFIG_DIR` [repro_issue_238.sh:LOCK_DIR] [repro_issue_248.sh:LOCK_DIR].
- `manual_test_helper.lua` opens the `README.md` in the repo root that holds the script, found from the script's own path when it loads (the cwd when the chunk has no file name), and returns early when that file is not readable [manual_test_helper.lua:repo_root, readme_path].
- `repro_issue_70_probe.lua` resolves the lock directory from `CLAUDE_CONFIG_DIR/ide`, else `$HOME/.claude/ide` [repro_issue_70_probe.lua:config_dir].
- The Lua repros call private plugin functions, for example `diff._setup_blocking_diff`, `selection._cancel_demotion_timer`, and `claudecode._create_commands`, so a rename in the plugin can break them. `repro_issue_208.lua` calls `_setup_blocking_diff` inside `pcall`: after a rename it prints `setup : ERROR` and still exits 0, which means fixed [repro_issue_208.lua:setup_ok] [repro_issue_246.lua:_cancel_demotion_timer] [repro_issue_285.lua:_create_commands].
- `release-please-runner.js` requires `GITHUB_TOKEN` and `GITHUB_REPOSITORY` in `owner/repo` form [release-please-runner.js:requireEnv, main].
- `assertLlmCredentials` throws when `ANTHROPIC_API_KEY` and `OPENAI_API_KEY` are both empty, or when `ANTHROPIC_API_KEY` and `COMMUNIQUE_MODEL` are both empty. An unset variable counts as empty, and the workflow passes `vars.COMMUNIQUE_MODEL` [release-please-runner.js:assertLlmCredentials].
- When default release-please notes have one line or fewer, the runner returns them without calling Communique [release-please-runner.js:releasePleaseNotesAreEmpty].
- `UnreleasedAwareChangelog` keeps the top `Unreleased` section and inserts new entries below it. It reads the changelog with commonmark.js, so a heading is a section only as a top-level block: a heading inside a code fence, an HTML block, a list item or a block quote is not one. The anchor is the first top-level heading whose own line is exactly `## [Unreleased]` or `## Unreleased`, or `### [Unreleased]` or `### Unreleased`, at the start of a line with one space after the marks and nothing but blanks after the text. These are the lines that the runner anchored on before it used a parser, and `## [Unreleased]` and `## Unreleased` are the lines that Communique 1.1.3 reads a draft under. Any other spelling is no anchor and its draft stays in the file: bold, emphasis or code, an escape, `[Unreleased][]`, two spaces or a tab after the marks, a closing `##`, a setext heading, an open or a closing bracket only, other text or a date, another case, an H1 and an H4. Without an anchor the entry goes under the title. Communique reads a draft under more lines than the update anchors on, so the update compares what the two read before it changes anything (see below). The draft is everything after it up to the next top-level heading of the anchor's level or a higher one (an H1 or H2 after an H2 anchor, whether it is an ATX heading with up to three spaces of indent, a heading with a tab after its marks, or a setext heading), or to the end of the text. The draft goes, so before it formats anything `updateContent` checks that the draft holds only paragraphs, lists and H3 headings with their inline code, links, images and inline HTML. An empty list item (a marker alone) is read. It refuses any other node, and any non-blank line that no paragraph or heading holds (a link reference definition leaves no node), with the line number and the first 80 code units of the line. A code fence keeps its own message, and any other node gives its commonmark.js type: `code_block (indented)`, `html_block`, `block_quote`, `thematic_break`, or a heading of another level (`heading (level 4)`, also an H1 or H2 inside a list item). Communique 1.1.3 does not parse Markdown. It reads the file as lines that end with LF alone and trims each line with Rust's `trim` (U+0009 to U+000D, a space, U+0085, U+00A0, U+1680, U+2000 to U+200A, U+2028, U+2029, U+202F, U+205F and U+3000). Its draft starts below the first line that is `## [Unreleased]`, `## Unreleased` or `## [Unreleased](...)`, and ends at the first later line that is `## ` and a version: a digit and a dot, or `v`, a digit and a dot, in brackets or not (`## 1.2`, `## [v0.4.1] - date`, and also `## 1. Install`). A code fence or a comment makes no difference to it. `findCommuniqueDraft` reads a file as Communique does. Communique folds the draft that it reads into the new entry. The update drops the draft that it reads itself and keeps every line after it, so it refuses unless both start and end the draft at the same line (`assertCommuniqueReadsTheSameDraft`), with the two lines in the message. That covers a line that CommonMark reads as text and Communique as a version heading (a no-break space before `## [0.4.1]`, or a lazy line with four spaces of indent), where the update would drop the lines below it. It covers an H1, an H2 that is no version (`## Upgrade notes`, `## v1`), a tab after the marks, an empty heading and a setext heading as the end of the draft too, where Communique reads on and the update would keep what Communique folded into the new entry, so it would show twice. And it covers the anchor: a `## [Unreleased](...)` link, an indent, a no-break space before the marks, or a heading in a code fence or a comment is an anchor for Communique and none for the update, so the update would add a second Unreleased heading and keep the draft. Communique does not end a line at a bare CR, so it does not see a heading that follows one on the same line. The update refuses when that makes the two find the heading or end the draft at different lines. It still accepts one shape, a bare CR that hides a second anchor line (left to R3b), and the format check rejects such a file. The cost: a draft with a code block, HTML, a block quote, a rule, a deeper heading or a link definition fails the run until a maintainer moves it out, and so does the draft of a first release that has one. Communique reads no draft under an H3 anchor, so a non-empty draft under `### [Unreleased]` or `### Unreleased`, whatever it holds, is refused with the line that starts it, and an empty one works (the H3 releases below it stay). An H3 heading directly under `## [Unreleased]` is a subsection of the draft, whatever it says, so `### [0.3.0]` there goes with the draft. After the formatter runs, `updateContent` compares the top-level headings of the formatted text with the headings that it expects, in this order and with the same levels, text and count: the headings of the new entry (read alone), then the headings of the kept older releases (read alone). Each is read with the link definitions of the whole text, so a reference link or image in a heading reads the same alone and in the formatted text. It refuses when the last top-level headings of the formatted text differ, for example when the new entry holds a code fence or an HTML comment that never closes (Prettier closes the fence at the end of the text, and the older releases are code or comment), even when the entry repeats an older release heading, or when Prettier moves a setext heading into a list item. A heading inside a list item or a block quote does not count there. Without an Unreleased heading, the entry goes under the title (found by the line reader), or under a new title, and the same check runs. The line reader `findLineOutsideFences` finds that title. `normalizeCommuniqueBody` demotes H2 headings of the generated entry. Both use `nextOpenFence`, so headings inside code fences are ignored, and a fence closes only on the same character, at least as long as its opener, so a four-backtick fence can hold a three-backtick line and a tilde fence can hold backticks. A line ends with LF, CR, or CR LF, and the updated changelog has LF endings only. A refused update fails the run when Release Please creates a release PR or changes its generated body, and the release PR keeps its last good content. So the run fails on each such run while the draft has a refused node. It skips the updater when an existing release PR's generated body is unchanged. `--dry-run` calls the updater on the local `CHANGELOG.md`, not on the one on `main`. A failed run exits with code 1 [release-please-runner.js:UnreleasedAwareChangelog, findUnreleasedDraft, assertDraftIsPlain, assertCommuniqueReadsTheSameDraft, findCommuniqueDraft, formatKeepingHeadings, findLineOutsideFences, splitLines].
- `formatChangelogSection` asserts a non-empty version and a `YYYY-MM-DD` date, and writes `## [VERSION] - DATE` without a `v` prefix [release-please-runner.js:formatChangelogSection].
- release-please reads its config and manifest from the remote target branch (`RELEASE_PLEASE_TARGET_BRANCH`, else the default branch when the variable is unset), not from the local checkout. An empty `RELEASE_PLEASE_TARGET_BRANCH` does not fall back to the default branch, because the runner uses `??`. Local edits to `release-please-config.json` take effect only after you push them [release-please-runner.js:main].
- The runner imports internal modules from `release-please/build/src/`, so it depends on the file layout of the pinned `release-please` version [release-please-runner.js:Simple, Changelog].
- `resolvePrettierBin` uses `PRETTIER_BIN`, then `scripts/node_modules/.bin/prettier`, then `prettier` on `PATH` [release-please-runner.js:resolvePrettierBin].
- `main` creates releases before release PRs [release-please-runner.js:main].
- A `check.sh` exits 2, in every mode, when `SKILL`, `MODEL` (or its model file), `SITE_RE`, `COVERED`, `RULES` or `FACTS` is empty, when it defines no `tla_constants`, when a `covered_block` file is missing from `COVERED`, when `EXPECT` has a key with a space, a key that names a non-fact, no entry for a fact, or a value that is not in `RULES`, `LIVE` or `-`, and when it calls `tla_main` without `tla_init`, in a pipe or a subshell, replaces the lib's `EXIT` trap, sources the lib twice, or ends without calling `tla_main`.
