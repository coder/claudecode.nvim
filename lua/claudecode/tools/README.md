# claudecode.tools

## Overview

`claudecode.tools` is the MCP tool registry and the set of tools that Claude Code can call in Neovim. The server ([`../server/README.md`](../server/README.md)) sends each `tools/list` request to `get_tool_list` and each `tools/call` request to `handle_invoke`. Each tool file returns a table `{ name, schema, handler, requires_coroutine? }`. `init.lua` registers these tables.

## Interface

### Registry (`init.lua`)

- `M.ERROR_CODES`: `PARSE_ERROR -32700`, `INVALID_REQUEST -32600`, `METHOD_NOT_FOUND -32601`, `INVALID_PARAMS -32602`, and `INTERNAL_ERROR -32000` [tools/init.lua:M.ERROR_CODES]
- `M.tools`: a map from tool name to `{ handler, schema, requires_coroutine }` [tools/init.lua:M.tools]
- `M.setup(server)`: stores the server and calls `register_all` [tools/init.lua:M.setup]
- `M.register(tool_module)`: requires `name` and `handler`. Otherwise it calls `vim.notify` at ERROR level and returns. It sends no MCP notification [tools/init.lua:M.register]
- `M.register_all()`: registers 10 exposed tools and the internal `close_tab` [tools/init.lua:M.register_all]
- `M.get_tool_list()`: returns `{ name, description, inputSchema }` only for tools that have a `schema` [tools/init.lua:M.get_tool_list]
- `M.handle_invoke(client, params)`: looks up `params.name` and runs the tool with `params.arguments` [tools/init.lua:M.handle_invoke]
- `M.build_response(ok, value, err)`: maps a handler outcome, as `pcall` or `coroutine.resume` returns it, to `{ result }` or `{ error }`. `handle_invoke` uses it, and so does `diff.open_diff_blocking` when it resumes a deferred tool [tools/init.lua:M.build_response]

## Invariants

- An unknown tool returns `{ error = { code = -32601, message = "Tool not found: <name>" } }` [tools/init.lua:M.handle_invoke]
- An error that is a `{ code, message }` table keeps its code, whether the handler raises it or returns `false, err`. This holds for tools with `requires_coroutine` too, also when the reply is sent after a deferred resume. Any other error maps to `-32000` [tools/init.lua:M.build_response] [diff.lua:M.open_diff_blocking]
- A successful handler returns `{ result = <value> }` [tools/init.lua:M.handle_invoke]. Each tool handler builds the MCP shape `{ content = { { type = "text", text = ... } } }` itself [tools/open_file.lua:handler]
- Tools with `requires_coroutine` run in `coroutine.create`. If the coroutine yields, `handle_invoke` returns `{ _deferred = true, coroutine, client, params }` and sends no response yet. Only `openDiff` sets `requires_coroutine = true` [tools/init.lua:M.handle_invoke]
- `openDiff` raises `-32602` when a required parameter is missing. Outside a non-main coroutine it raises `-32000` with `message = "Internal server error"` and `data = "openDiff must run in coroutine context"` [tools/open_diff.lua:handler]
- `openDiff` calls `diff.open_diff_blocking(old, new, contents, tab_name, client.id)`. Structured errors pass through. Other errors become `-32000` "Error opening blocking diff" [tools/open_diff.lua:handler]
- `openFile`, `checkDocumentDirty`, and `saveDocument` raise `-32602` when `filePath` is missing [tools/open_file.lua:handler]
- `openFile` raises `-32602` before it opens the file when `startLine` or `endLine` is given but is not an integer (`false` included), `startLine` is below 1 or past the last line, or `endLine` is below `startLine`. The last line comes from the loaded buffer that `:edit` would reuse, which `bufexists()` and `bufadd()` find by name or by the inode Neovim cached for it, so a symlink or hard link finds it. Without one it comes from the file on disk. For a loaded buffer without unsaved changes the file on disk counts too, because openFile loads the file again when it changed. When the buffer openFile then shows has fewer lines than `startLine`, openFile selects its last line. An `endLine` past the last line selects through the last line, and the answer names the lines it selected [tools/open_file.lua:handler]
- `openFile` raises `-32000` with `message = "File operation error"` and `data = "File not found: <path>"` when the file is not readable, and with `data = "No preview window shows the file"` when the preview window is closed or no longer has 'previewwindow' set after it gets the file, for example because an autocommand cleared it. It raises `-32000` and changes nothing while the command-line window is open, and when the user is in the middle of a command in the preview window, which openFile would reuse. Its defaults are `preview=false`, `makeFrontmost=true`, and `selectToEndOfLine=false` [tools/open_file.lua:handler]
- `checkDocumentDirty` and `saveDocument` return a `success=false` JSON result (not an error) when the file has no open buffer [tools/save_document.lua:handler]
- `getDiagnostics` raises `-32000` when `vim.lsp`, `vim.diagnostic`, or `vim.diagnostic.get` is missing. It raises `-32001` "File not open" when no buffer exists for `uri` (`vim.fn.bufnr(path) == -1`). An unloaded buffer does not raise [tools/get_diagnostics.lua:handler]
- `getLatestSelection` returns a `success=false` JSON result when no selection exists [tools/get_latest_selection.lua:handler]
- With no selection, `getCurrentSelection` returns `success=false` only when the active buffer has no name. When a named buffer is active, it returns `success=true` with an empty selection [tools/get_current_selection.lua:handler]
- `close_tab` returns its error tables as values, not raised errors. `handle_invoke` therefore wraps them in `result`. It answers `TAB_CLOSED` when it closes the diff, when it keeps a diff the user accepted for another client, and when no diff has that name [tools/close_tab.lua:handler]

## Side Effects

- `openFile` runs `edit` in the main editor window, the first window that is not floating, a terminal, prompt, or `nofile` buffer, a diff window, the preview window, or a file-explorer or outline sidebar. With preview it shows the file in the preview window of that tab page instead, and makes one as `pedit` does when the tab page has none. Like `pedit`, it shows the file there even when that window has 'winfixbuf' set. A buffer that is already loaded is not re-read, so its unsaved changes and the folds of other windows on it stay. When its file changed on disk, openFile loads a buffer without unsaved changes again, as `:edit` does, and keeps a buffer with unsaved changes as it is, without asking the user. For that it adds a FileChangedShell autocommand for the buffer that runs after the user's and sets `v:fcs_choice`, so 'autoread' and a user's `v:fcs_choice` do not change the result. 'eventignore' or, on Neovim 0.11 and later, 'eventignorewin' can make Neovim skip that autocommand. For a window that already shows the buffer, openFile reads them as Neovim does, where 'eventignorewin' counts for the current window when it shows the buffer and otherwise only when every window that shows the buffer ignores the event. When the event is ignored there, openFile checks the file only with 'autoread', which loads it without asking, so with 'noautoread' the buffer keeps the old text. When openFile shows the buffer in a window that did not show it, and 'eventignore', or 'eventignorewin' of that window or of a window that shows the buffer, ignores the event, openFile turns Neovim's own check off for that step and then checks the file as for a window that shows the buffer. Autocommands that run during that step see the buffer's 'buftype' set to `acwrite`, which keeps 'modified' as it is. A plugin that skips buffers whose 'buftype' is set skips this one in those autocommands, until a window enters it again, and an autocommand that sets 'buftype' to `acwrite` itself is undone. A write of an `acwrite` buffer skips Neovim's E13 and changed-file checks and goes to BufWriteCmd. So when a user's `++nested` BufEnter, BufWinEnter or BufLeave autocommand writes the buffer during that step, and a user's BufWriteCmd autocommand that matches the file (such as `BufWriteCmd *`) writes `<afile>`, that handler writes the buffer over the file. Without `++nested` no BufWriteCmd runs and the write fails with E676. Without such a handler it fails the same way. Outside that step, a write of a buffer with unsaved changes whose file Claude changed is a normal write. When a user's autocommand starts one while openFile switches buffers or windows, for example `autocmd BufLeave * silent! wall`, Neovim asks "The file has been changed since reading it!!! Do you really want to write to it (y/n)?", and openFile answers Claude only after the user does. `y` writes the unsaved text over Claude's file. `n` or Escape writes nothing, and the buffer keeps its unsaved text. CTRL-C writes nothing, leaves the focus where it was, and fails openFile with "Keyboard interrupt". Other keys repeat the question. After `y` the answer to Claude also waits for Enter at Neovim's hit-enter prompt, on 0.8 and 0.10, and on 0.12 with the default 'messagesopt'. A buffer whose 'buftype' is already set is not checked, as Neovim does not check it. A buffer opened before its file existed, for which Neovim fired BufNewFile, gets the same step, because Neovim's question for it, W13, runs no FileChangedShell. Without unsaved changes openFile reads the file into it with `:edit`, except during Visual or Select mode that CTRL-O started, which `:edit` would end, and except when an autocommand showed another buffer in the window. Then the buffer keeps its text. With unsaved changes it keeps them, and a later `:w` fails with E13 until `:w!`. openFile knows such buffers from the time the Claude Code server starts. A buffer loaded before then counts when its file was missing at that time. No Neovim API tells such a buffer apart, so W13 can still come for one whose file appeared before the server started, or that was made while 'eventignore' ignored BufNewFile. A write that runs no BufWritePost does not end the tracking: one from an autocommand without `++nested`, such as `autocmd BufLeave * update`, or one through a BufWriteCmd handler. openFile then keeps running its acwrite step for that buffer, and reads the file into it again with `:edit` when it has no unsaved changes. Neovim no longer asks W13 for that buffer, but it asks W12 when the buffer has unsaved text and its file changed. The acwrite step turns Neovim's check off, so no question comes, and unsaved text stays. Neovim can still ask when a user's FileChangedShell autocommand deletes openFile's: the user's autocommand then decides alone. An error in a user's autocommand fails openFile. Run from Lua, such an error during a reload stops the reload halfway and leaves the old text with empty lines added, while Neovim takes the file as read. So when the reload began, openFile reads the file again under `:silent!`, as a `:checktime` that the user types would finish, before it fails: the buffer gets the whole file, and that read ends Visual mode. After a FileChangedShell error no reload begins: the buffer keeps the old text, and a later `:w` warns that the file changed. When no suitable window exists, it can split or move windows. It splits instead of editing into a diff or preview window, splits the window below the preview window instead of the preview window itself, and with `makeFrontmost=false` gives the focus back to the window that had it. With preview it splits only to make the preview window when the tab page has none, so a terminal keeps one window. Then it works in the window that shows the file. For line or text ranges it searches that window's buffer and sets the visual marks and the cursor there. `makeFrontmost` focuses that window, and with `makeFrontmost=false` the JSON answer describes its buffer. Visual mode exists only in the current window, so with `makeFrontmost=false` and another window current, the marks are set but no selection stays on. With preview this holds even when the current window shows the same file, because the file goes to the preview window. With 'selection' set to inclusive, a range that ends on an empty line also covers that line's line break. When `endText` is not found, it only places the cursor on the `startText` match. It never changes the buffer. It ends any Visual or Select mode before it selects, it always selects charwise, and `gv` is the last key it sends, so with 'selectmode' containing `cmd` the selection is left in Select mode. When the user is in the middle of a command, it leaves the current window, its cursor, and the mode alone. That covers an operator such as `d` that waits for its motion, Insert mode, Replace mode, CTRL-O from them, and the command line. On Neovim 0.10 and later it also covers Visual or Select mode that CTRL-O started, which `state()` shows as `S`. On 0.8 and 0.9 that mode looks like plain Visual mode, so openFile ends it and selects as usual: after the call the mode is `v` with Claude's selection in the opened file, the user's next Visual command acts on that selection, and Insert mode then resumes in the opened file. It shows the file in the preview window, places the cursor there, selects nothing, does not focus it, and sends no keys, so the user's next keys finish the command where it started. When the command runs in the buffer of that file, the rules above can still load the file into it, and the user's next keys then act on the new text. The answer says so, except the `makeFrontmost=false` JSON. A register prefix such as `"a` looks like Normal mode, so openFile works as usual and the user's next command acts in the opened file. A count or a prefix such as `g` or CTRL-W blocks Neovim, which reads no request until the next key [tools/open_file.lua:handler]
- `openDiff` opens a blocking diff through `claudecode.diff`. The response stays deferred until the user accepts or rejects the diff [tools/open_diff.lua:handler]. A diff that resolves before `openDiff` yields, for example from a `ClaudeCodeDiffOpened` handler, is answered at once [diff.lua:M.open_diff_blocking]
- `saveDocument` runs `write` in the matching buffer with `nvim_buf_call` [tools/save_document.lua:handler]
- `closeAllDiffTabs` calls `diff.close_all_diffs` and returns `CLOSED_<n>_DIFF_TABS` [tools/close_all_diff_tabs.lua:handler]
- `close_tab` calls `diff.close_diff_by_tab_name` with the tab name and the calling client. It closes or deletes no other buffer, whatever the name [tools/close_tab.lua:handler]
- `getCurrentSelection`, `getLatestSelection`, `getOpenEditors`, `getDiagnostics`, `getWorkspaceFolders`, and `checkDocumentDirty` only read editor state [tools/get_open_editors.lua:handler]
- `handle_invoke` writes debug log entries through `claudecode.logger` [tools/init.lua:M.handle_invoke]
