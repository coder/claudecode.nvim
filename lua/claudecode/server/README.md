# claudecode.server

## Overview

`claudecode.server` is the plugin's built-in Model Context Protocol (MCP) server. It is a pure-Lua WebSocket (RFC 6455) server on top of `vim.loop` TCP handles. It speaks JSON-RPC 2.0 to the Claude Code CLI. It listens only on `127.0.0.1`, checks an auth token during the HTTP upgrade, and sends MCP tool calls to [`../tools/README.md`](../tools/README.md).

Layers, top to bottom:

1. `init.lua`: server lifecycle, MCP method table, JSON-RPC dispatch, and deferred responses.
2. `tcp.lua`: port selection, listen socket, client registry, and the keep-alive ping timer.
3. `client.lua`: per-connection state machine (handshake, then frames).
4. `handshake.lua` and `frame.lua`: HTTP upgrade validation and frame encode/decode.
5. `utils.lua`: base64, SHA-1, masking, UTF-8, and constant-time compare helpers.

`mock.lua` is an in-memory stand-in with no sockets. Nothing in `lua/` requires it. `tests/unit/server/mock_spec.lua` tests its `broadcast`.

## Interface

### Lifecycle and messaging (`init.lua`)

- `M.state`: `{ server, port, auth_token, handlers, ping_timer, in_flight }`, where `in_flight` holds the requests whose handler is running [server/init.lua:M.state]
- `M.start(config, auth_token) -> ok, port|err`: registers handlers, calls `tools.setup(M)`, creates the TCP server, and starts the ping timer. It returns "Unknown server creation error" when `create_server` fails without a message [server/init.lua:M.start]
- `M.stop() -> ok, err?`: stops the ping timer, closes pending diffs, answers each request whose handler is still running, stops the TCP server, and clears deferred responses [server/init.lua:M.stop]
- `M.register_handlers()`: handles `initialize`, `notifications/initialized`, `prompts/list`, `tools/list`, and `tools/call` [server/init.lua:M.register_handlers]
- `initialize` returns `protocolVersion = "2024-11-05"` (`MCP_PROTOCOL_VERSION`), `capabilities` (logging, `prompts.listChanged`, `tools.listChanged`), `serverInfo.name = "claudecode-neovim"`, and `serverInfo.version = require("claudecode").version:string()` [server/init.lua:MCP_PROTOCOL_VERSION] [server/init.lua:M.register_handlers]
- `tools/call` checks the shape of its params first, then delegates to `tools.handle_invoke` and returns a `_deferred` table (`{ _deferred = true, coroutine, client, params }`) for blocking tools
  [server/init.lua:M.register_handlers]
- Handler contract: a request handler returns `result, error_data`. A truthy `error_data` becomes the error reply [server/init.lua:M._handle_request]
- `M.send(client, method, params) -> boolean`: sends a JSON-RPC notification to one client [server/init.lua:M.send]
- `M.send_response(client, id, result, error_data) -> boolean`: a `nil` id is sent as JSON `null` (`vim.NIL`) [server/init.lua:M.send_response]
- `M.broadcast(method, params, on_written?) -> boolean`: sends a notification to every `connected` client, and returns true only when at least one took it. When one did, `on_written(written)` runs once after the last write finished, with how many writes succeeded: a socket that fails during the write reports it only there [server/init.lua:M.broadcast] [server/tcp.lua:M.broadcast]
- `M.get_status() -> { running, port, client_count, clients }`. `clients` is present only while the server runs [server/init.lua:M.get_status]
- Internal dispatch: `M._handle_message`, `M._handle_request`, `M._handle_notification`, and `M._setup_deferred_response` [server/init.lua:M._handle_message]

### TCP server (`tcp.lua`)

- `M.create_server(config, callbacks, auth_token) -> server|nil, err`: tries ports in the configured range until one binds and listens [server/tcp.lua:M.create_server]
- `M.find_available_port(min_port, max_port)`: probe-only port check. Nothing in `lua/` calls it [server/tcp.lua:M.find_available_port]
- `M.send_to_client`, `M.broadcast`, `M.get_client_count`, and `M.get_clients_info` [server/tcp.lua:M.send_to_client]
- `M.stop_server(server)`: closes the check and idle handles of a keepalive or stall judgement that has not run, sends a Close frame with code 1001 "Server shutting down" to clients that finished the handshake
  or whose 101 reply is still being written, closes the TCP handle of the others, empties `server.clients`, then closes the listener. It calls no `on_disconnect`. It skips a client that is already
  `closing` or `closed`, or whose socket is already closing: that client gets no Close frame. A client that sent its own Close frame is `closing`, and it stays in `server.clients` until its scheduled `on_close` runs. If `stop_server`
  runs first, that `on_close`, or a later EOF, closes the client's socket in `_disconnect_client` [server/tcp.lua:M.stop_server] [server/client.lua:M.close_client] [server/client.lua:M.process_data]
  [server/tcp.lua:M._disconnect_client]
- `M.start_ping_timer(server, interval)`: default interval is 30000 ms. It sets `server.keepalive_timeout` to `interval * 2`, and clients accepted from then on carry it [server/tcp.lua:M.start_ping_timer]
- Internal: `M._bind_and_listen`, `M._handle_new_connection`, `M._disconnect_client`, and `M._remove_client` [server/tcp.lua:M._bind_and_listen]

### Connection, handshake, and frames

- `client.create_client(tcp_handle, keepalive_timeout?)`, `process_data(...)`, `send_message`, `send_ping`, `close_client`, `abandon_close_frame`, `sample_write_progress(client)`, `is_client_reading(client)`, and `get_client_info` [server/client.lua:M.process_data]
- Client states: `connecting`, then `upgrading` (101 reply being written), then `connected`. `close_client` moves an `upgrading` or `connected` client to `closing`, then to `closed` when the write callback of its Close frame runs, or when the Close frame deadline closes the socket. It moves a `connecting` client, or one whose socket is already closing, straight to `closed`. A rejected handshake and a received Close frame set `closing`, and the state never becomes `closed`. An EOF or a read error changes no state [server/client.lua:M.create_client] [server/client.lua:M.close_client] [server/client.lua:M.process_data]
- `client.get_client_info(client) -> { id, state, handshake_complete, buffer_size, last_ping, last_pong, connected_at }`. `connected_at` is the loop time when the handshake completed, and `nil` before. `buffer_size` counts the unparsed bytes and the reads of an unfinished frame. `tcp.get_clients_info` returns these tables [server/client.lua:M.get_client_info]
- `client.send_message` calls its callback with "Client not connected" and writes nothing unless the state is `connected`. `send_ping` does nothing unless the state is `connected` [server/client.lua:M.send_message] [server/client.lua:M.send_ping]
- `handshake.process_handshake(request, expected_auth_token) -> ok, response, headers?` [server/handshake.lua:M.process_handshake]
- `handshake.validate_upgrade_request`, `create_handshake_response`, `parse_request_line`, `is_websocket_endpoint`, `create_error_response`, and `extract_http_request` [server/handshake.lua:M.validate_upgrade_request]
- `handshake.create_error_response(code, message)`: a plain-text HTTP response with `Connection: close`, for 400, 404, 426, 500, or any other code [server/handshake.lua:M.create_error_response]
- `frame.OPCODE`: `CONTINUATION 0x0`, `TEXT 0x1`, `BINARY 0x2`, `CLOSE 0x8`, `PING 0x9`, `PONG 0xA` [server/frame.lua:M.OPCODE]
- `frame.MAX_PAYLOAD_LENGTH`: 100 MiB, the largest frame payload and the largest message [server/frame.lua:M.MAX_PAYLOAD_LENGTH]
- `frame.parse_frame(data, start?) -> frame|nil, consumed, close_code?, detail?`: parses the frame that starts at byte `start` (default 1). `nil, 0` means incomplete, and `nil, 0, nil, length` gives the whole frame's length once its header arrived. `nil, 0, code, problem` means fatal, with the broken rule in `problem` [server/frame.lua:M.parse_frame]
- `frame.create_frame`, `create_text_frame`, `create_binary_frame`, `create_close_frame`, `create_ping_frame`, `create_pong_frame`, and `is_control_frame` [server/frame.lua:M.create_frame]

### Helpers (`utils.lua`)

- `generate_accept_key`, `sha1`, `base64_encode`, `base64_decode`, `generate_websocket_key`, `parse_http_headers`, `is_valid_utf8`, `apply_mask`, `constant_time_compare`, `uint16_to_bytes`, `uint64_to_bytes`, `bytes_to_uint16`, and `bytes_to_uint64` [server/utils.lua:M.generate_accept_key]

### Mock (`mock.lua`)

- `M.state`, `start`, `stop`, `register_handlers` (`mcp.connect`, `mcp.tool.invoke`), `add_client`, `remove_client`, `send`, `send_response`, `broadcast`, `simulate_message`, and `clear_messages` [server/mock.lua:M.register_handlers]
- `M.find_available_port(min, max)`: always returns `min` [server/mock.lua:M.find_available_port]

## Invariants

- The server listens only on `127.0.0.1` with backlog 128. It closes the handle if bind or listen fails [server/tcp.lua:M._bind_and_listen]
- The port iterator yields each port in the range exactly once, starting at a random offset. `create_server` returns "No available ports in range min-max" for an empty range, and "No free port in min-max (<libuv error code>)", for example `(EADDRINUSE)`, when every port fails [server/tcp.lua:M.create_server]
- `M.start` refuses with "Server already running" when `M.state.server` is set. `M.stop` returns "Server not running" when it is not set. `send`, `send_response`, and `broadcast` return `false` without a server [server/init.lua:M.start]
- While the server runs, `send` and `send_response` return `true` even for an unknown or unconnected client: they pass no callback, so `tcp.send_to_client` drops the message silently [server/init.lua:M.send_response] [server/tcp.lua:M.send_to_client]
- A failed `M.start` leaves `M.state.auth_token`, the handlers, and `tools.setup(M)` in place, with `M.state.server` still `nil`, so a retry is allowed. `M.start` returns `true` even when the ping timer could not be created. Only `on_error` logs that failure [server/init.lua:M.start] [server/tcp.lua:M.start_ping_timer]
- `on_connect` fires when the TCP connection is accepted, before the WebSocket handshake and the auth check. It only logs. `process_mention_queue(true)` waits for `on_open`, after the handshake. `client_count` includes clients that have not finished the handshake [server/tcp.lua:M._handle_new_connection] [server/init.lua:M.start]
- When an auth token is set, the upgrade request must carry `x-claude-code-ide-authorization`. The header length must be 10..500. The token is compared with `utils.constant_time_compare` [server/handshake.lua:M.validate_upgrade_request]
- The upgrade request must have `Upgrade: websocket`, `Connection` containing `upgrade`, `Sec-WebSocket-Version: 13`, and a 24-character `Sec-WebSocket-Key` [server/handshake.lua:M.validate_upgrade_request]
- A non-GET or non-HTTP/1.1 request gets 404. A failed validation gets 400 "Bad WebSocket upgrade request: <reason>". A failed accept key gets 500 "Failed to generate WebSocket handshake response" [server/handshake.lua:M.process_handshake]
- `is_websocket_endpoint` accepts any path. `Sec-WebSocket-Key` is checked for its length only, not for base64. The 101 reply echoes the client's `Sec-WebSocket-Protocol` value verbatim [server/handshake.lua:M.is_websocket_endpoint] [server/handshake.lua:M.validate_upgrade_request] [server/handshake.lua:M.create_handshake_response]
- `parse_http_headers` lower-cases header names. A later duplicate header wins. A value keeps its trailing whitespace, and a header with an empty value is dropped, so `Upgrade: websocket ` with a trailing space fails the upgrade check [server/utils.lua:M.parse_http_headers]
- No timer closes a client that never finishes the handshake. The ping timer checks only `connected` clients, and `client.buffer` grows until the request's `\r\n\r\n` arrives. Only EOF, a read error, or `stop_server` removes such a client [server/tcp.lua:M.start_ping_timer] [server/client.lua:M.process_data]
- Frames are dispatched only after `handshake_complete` is true. The state becomes `connected` only after a successful handshake. While its 101 reply is written, a client is `upgrading`: the bytes it sends then wait in its buffer for the write callback, so its request is answered once and its first frames are kept. libuv runs the write callback before the server reads a later EOF. So a client that hung up after its request is still open at the callback, unless the server read its EOF in the same read as the request. The callback then sets `connected` and parses the buffered frames, and the next rule decides whether each request runs. Only when the socket is already closing does the callback drop the buffered bytes and leave the client `upgrading`. When the write fails, for example with `ECONNRESET`, the callback calls `on_error`, which removes the client and closes its socket. When the server stops first, `close_client` clears the buffer and sets `closing`, and the callback returns without a state change [server/client.lua:M.process_data] [server/client.lua:M.close_client]
- A whole message runs through `on_message` only if, when the main loop gets to it, the client is still `connected` and its socket is open. A request from a client that hung up or sent its Close frame meanwhile does not run [server/client.lua:M.process_data]
- A text message can arrive in fragments (a TEXT frame with FIN clear, then CONTINUATION frames up to one with FIN set), with control frames between them. `process_data` joins the fragments and calls `on_message` once with the whole text. Only the whole message must be well-formed UTF-8, and one that is not closes with 1007. A binary message closes with 1003, and nothing runs it. A CONTINUATION frame with no message to continue, or a TEXT or BINARY frame inside a fragmented message, closes with 1002. A message whose fragments add up to more than `frame.MAX_PAYLOAD_LENGTH` (100 MiB) closes with 1009. Each Close frame carries the RFC 6455 name of its status as the reason: `Protocol error` (1002), `Unsupported data` (1003), `Invalid frame payload data` (1007) or `Message too big` (1009) [server/client.lua:add_data_frame] [server/client.lua:M.process_data]
- `process_data` parses every frame of one read from an offset into its buffer and keeps the unparsed rest once at the end, so many small frames in one read cost linear time. The reads of a frame longer than one read wait in `client.pending` until the whole frame arrived, and are joined once, so a large frame costs linear time too [server/client.lua:M.process_data]
- `parse_frame` rejects set RSV bits, invalid opcodes, fragmented control frames, and control payloads over 125 bytes with 1002. It rejects a payload over `MAX_PAYLOAD_LENGTH` (100 MiB) with 1009, and a close reason that is not well-formed UTF-8 with 1007. It rejects a Close payload of 1 byte with 1002. It names the broken rule (for example `Reserved opcode 0x3`). `process_data` passes that name to `on_error`, so the client's disconnect reason is `Client error: <rule>` with code 1006, while the Close frame carries the RFC 6455 status name. `parse_frame` does not check the UTF-8 of a text frame, because a fragment can end inside a code point. `is_valid_utf8` uses `utils.utf8_sequence_length`, the decoder behind the outbound `utils.valid_utf8`, so it also rejects overlong forms, UTF-16 surrogates, code points above U+10FFFF, and the bytes C0, C1 and F5 to FF [server/frame.lua:M.parse_frame] [server/utils.lua:M.is_valid_utf8]
- `parse_frame` does not reject unmasked client frames, non-minimal length encodings, or any Close status code. Server frames are unmasked by default (`masked=false`) [server/frame.lua:M.parse_frame] [server/frame.lua:M.create_frame]
- `create_frame` and `create_close_frame` do not check the payload size, so a Close reason over 123 bytes makes a control frame that breaks RFC 6455 [server/frame.lua:M.create_close_frame]
- A received Close frame with an empty payload counts as code 1000 with an empty reason. A `connected` client gets its code and reason echoed back, the state becomes `closing`, `on_close` is scheduled, and later bytes are dropped. A PING gets a PONG with the same payload. Any PONG sets `last_pong`, which only `get_client_info` reads. The keepalive uses `ping_unanswered_since`, which any bytes clear [server/client.lua:M.process_data] [server/tcp.lua:M._handle_new_connection]
- Every text frame the server sends is valid UTF-8. `send_message` replaces each ill-formed sequence with U+FFFD, so a buffer name or path with invalid bytes reaches the client as U+FFFD and does not drop the connection [server/client.lua:M.send_message]
- JSON-RPC errors: -32700 for a parse error and -32600 unless `jsonrpc == "2.0"` [server/init.lua:M._handle_message]. -32601 for an unknown method and -32603 for a handler that raises [server/init.lua:M._handle_request]. `tools/call` answers `-32602` "Invalid params" before it runs a tool when `params` is not an object, `name` is not a string, or `arguments` is present and is not an object. The only log line of a rejected call is one debug line (see below). A JSON array is not an object, so `[]` and `[1]` both get `-32602`, as `params` and as `arguments`. A request without `params` gets `-32602` naming `params`: `_handle_request` passes a plain `{}`, and a plain `{}` counts as a list. `"params": {}` is an object and gets `-32602` naming `name`. `vim.json.decode` gives `[]` a table without the empty-dict mark and `{}` a table with it, and `vim.islist` (`vim.tbl_islist` before Neovim 0.10) tells them apart. A call without `arguments` is valid: the tool gets `{}` [server/init.lua:M.register_handlers] [tools/init.lua:M.handle_invoke]
- When the JSON decodes to a non-table value (for example a number or a boolean), `_handle_message` replies -32600 with `"id": null`. It does not raise [server/init.lua:M._handle_message]
- A message with a truthy `id` is a request. Any other message is a notification. A valid notification never gets a response. The -32700 and -32600 checks run before the `id` check, so a malformed notification gets an error reply [server/init.lua:M._handle_message]
- Notification handlers run in `pcall`. Their errors and return values are discarded, and an unknown notification is ignored without a reply [server/init.lua:M._handle_notification]
- A deferred response is keyed by `tostring(coroutine)` in `_G.claude_deferred_responses`. It replies to `result.client` with the original request id. A result with `content` is sent as `result`, one with `error` is sent as `error`, and a result with neither becomes -32603 [server/init.lua:M._setup_deferred_response]
- `_handle_request` records each request in `M.state.in_flight` while its handler runs. `M.stop` sends -32603 "Internal error" (`data`: "The server stopped before the call finished") for every request still recorded, before it stops the TCP server, and `_handle_request` sends nothing for that request afterwards. A blocking tool has no response sender before its handler yields, so nothing else can answer a request whose handler is still running [server/init.lua:M._handle_request] [server/init.lua:M.stop]. The README at the repository root, under Global Invariants, lists what Claude receives at an exit.
- A ping timer tick pings every connected client and never closes one for a missing answer. `client.ping_unanswered_since` holds the loop time of the oldest ping sent since bytes were last read from the client. The read callback clears it on any bytes, not only a pong: Claude shows it is alive by writing anything, and a pong that waits behind more unread data than the socket holds is not in the first poll after a block. The tick calls `vim.loop.update_time()` before it reads the clock, because libuv caches the loop time when a pass of the main loop starts and runs the timers of the pass with it, and a callback that ran before the tick in the pass can have blocked since, or the machine can have slept in it. A stale time would hide a wake and would stamp a ping older than it is. Each tick that pinged a client arms `after_next_poll` (below), and its callback runs `judge_silence` after the next poll. libuv runs the check handle right after the poll phase that reads the sockets, so every byte that reached a socket before that poll started was read. The check closes each client that the tick pinged when its oldest ping is `interval * 2.5` old, but only if its loop time is at most `interval * 1.5` after the tick. After a longer block Neovim and Claude can have slept together (a suspended machine), and Claude has had no time to answer. A tick cannot decide this, because libuv can run a tick before it reads the pong that Claude sent: after a block in a check callback or an I/O read callback, and, with libuv 1.44 (bundled in Neovim 0.8), after a block in any callback. libuv 1.44 also runs the timers again at the end of a pass, so two ticks can run with no read between them. `vim.schedule` cannot decide it either, because Neovim runs its callbacks between two passes, so it can run one before the read. Drop bound: a Claude that answers each ping before the next tick is not closed by a block of the main loop of any length in any callback, or by a sleep of the machine. A tick never closes a client, a check judges only after a poll within `interval * 1.5` of its tick, and any bytes clear the stamp. A pong that comes later than one interval can wait unread in a socket: a callback that blocks inside the poll phase after the poll took its snapshot, and that refreshes the loop time, leaves the bytes that arrived during the block unread, and the check then closes the client once its oldest ping is `interval * 2.5` old (75 s by default). A real Claude answers a ping at once. A client that writes data but never answers a ping is not closed by this rule: it is alive, and the plugin does not judge what it writes (the stall rule below closes it when it stops reading, but only once the kernel's socket buffers are full and libuv's write queue backs up, because a queue that is empty counts as progress). A tick more than `interval * 1.5` after the tick before it is a wake: it takes the gap for a sleep, clears every stamp and restarts the count. A block of more than half an interval that starts just before a tick is enough, so a run of such blocks can postpone the close of a silent Claude. A silent Claude is closed by the first check that finds its oldest unanswered ping `interval * 2.5` old. That is 90 s after the ping when the ticks come on time. A tick that runs late moves the ticks after it back, so one late tick delays the close. Two late ticks in a row, or a poll that a block delays after a tick, can bring the close as early as 75 s, and never earlier. The Close frame of a dropped client carries 1011 "Keepalive timeout" (RFC 6455 reserves 1006, so no Close frame carries it), `on_disconnect` gets 1006 "Connection timeout", and the check logs `Closed client_<n>: no reply for <s>s` at info level. A peer that stopped reading does not get that Close frame: once its receive window is full, every write to it (replies, pings, and the Close frame) waits in libuv's queue, and closing the socket drops the queue [server/tcp.lua:M.start_ping_timer] [server/tcp.lua:judge_silence] [server/tcp.lua:drop_client]
- A Claude that answers each ping but never reads would keep that queue, which is Neovim's memory, without limit, so the server also closes a connected client that answers and whose write queue made no progress at two ticks in a row. Each tick calls `is_client_reading` for each connected client, which calls `sample_write_progress`: it compares `queued_bytes - get_write_queue_size()` with its value at the last progress, and an empty queue counts as progress. A tick that finds progress clears `client.write_stalled`. The first tick that finds none sets it. The second asks for a confirmation, and a confirmation that still finds no progress drops the client: the Close frame carries 1011 "Not reading", `on_disconnect` gets 1006 "Write queue stalled", and the server logs `Closed client_<n>: not reading for <s>s, <n> KB queued` at info level. The confirmation runs right after the next poll. libuv reports that a socket is writable again only in a poll phase, so a tick that Neovim runs after a main-loop block inside an I/O callback can find no progress although Claude read during the block, whether the tick is late or on time. `after_next_poll` arms a check handle, which libuv runs right after each poll phase in every version, and an idle handle, which keeps that poll from waiting for a timer or a socket. The check callback closes both handles, removes them from `server.pending_polls`, and judges the queue once more: progress clears `write_stalled`, and no progress drops the client. A client that left or started to leave in the meantime, because the poll read its EOF, a read error, its Close frame or a protocol error, is skipped without a log line. `stop_server` closes the handles of a confirmation that has not run, which `server.pending_polls` lists. If libuv cannot create a handle, the tick leaves the client for the next tick. The look is a sample at one moment, not proof. libuv takes its snapshot of the ready sockets when a poll starts, so a callback that blocks inside that poll, after the snapshot, hides what Claude reads during the block from the check callback that follows. A client that was stalled for the whole window and resumes during such a block is dropped. That is a deadline race, as with any timeout: the client was stalled when the window ended, and what it read afterwards is not reported yet. Verifier probes closed a reader that resumed 0.1 s into a 0.5 s to 1.5 s block inside the confirming poll, on Neovim 0.12.3 and 0.8.0, at 3 s, 5 s and 30 s intervals. A block after the tick and before that poll, or in a scheduled callback, keeps the reader. The bound is two to three ticks after the last progress, which is 60 s to 90 s at the default interval, plus the delay of late ticks, each of which comes at most `interval * 1.5` after the tick before it. A tick that comes more than `interval * 1.5` after the tick before it counts as a wake from sleep. A wake tick starts a fresh stall window: it clears the count and judges nothing, so it delays the drop by one tick when the count was clear, and by two ticks when the wake tick takes the place of the confirming tick. The next two ticks always count, wake ticks or not, because wake ticks that come again and again are a loop that stays blocked, not sleeps. So whatever the pattern of late ticks, a stalled client is closed at the second tick after a fresh window started. A wake tick three or more ticks after the last fresh start starts a new window. The bound is never the size of the queue, so a Claude that reads slowly, or is sent one message of tens of MB, stays connected while libuv writes any of it. libuv writes more only after the kernel reports the socket writable again, which took 1.2 to 1.5 MB of reading on a Linux loopback socket with default buffers (measured), so a Claude that reads less than about 1.4 MB per window counts as stalled while a backlog exists, and one that reads just faster than that still lets the queue grow as long as Neovim queues more than it reads. `write` queues a frame of more than 1 MiB in pieces of 1 MiB, because libuv on Windows lowers the queue only when a whole write request is done, so a large frame shows its progress per piece there too, and the callback of the last piece reports the frame. [server/tcp.lua:M.start_ping_timer] [server/tcp.lua:judge_stall] [server/tcp.lua:after_next_poll] [server/tcp.lua:M.stop_server] [server/client.lua:M.is_client_reading] [server/client.lua:M.sample_write_progress] [server/client.lua:write]
- On one tick a client counts as answered when no ping of it waited for `interval * 2`. Only a client that answered is confirmed for a stall. A client that did not answer is dropped by the keepalive check above, whatever its write queue shows. A client that answers while its queue is stalled is not saved: its bytes clear the stamp, the next tick finds it answered, and then asks for the confirmation. Every connected client is sampled on every tick except one that starts a fresh stall window, answering or not, so "two ticks in a row" means consecutive ticks. A tick gap above `interval * 1.5` counts as a wake from sleep and clears `ping_unanswered_since` of each connected client. A wake tick that starts a fresh stall window also resets `last_drain`, clears `write_stalled`, and does not sample the queue. `last_drain` feeds only the `not reading for <s>s` of the log line, so the reset keeps the sleep out of it. A wake tick within two ticks after the start of a fresh window clears the stamps only, and counts like any tick. A client that is not connected is not pinged, so a main loop that blocks during the handshake does not count against it [server/tcp.lua:M.start_ping_timer] [server/client.lua:M.process_data]
- `_disconnect_client` is idempotent: `on_disconnect` fires once per client id. A client that already left the server (the server stopped before a scheduled `on_close` or an EOF ran) gets its socket closed there, unless the write callback of its Close frame will close it [server/tcp.lua:M._disconnect_client]
- A client's EOF, read error, or protocol error reaches the server only as its `on_disconnect` code 1006 and reason (`EOF`, `Client read error: …`, or `Client error: …`), which `init.lua` logs at debug level. The server's `on_error` callback, not the `on_error` argument of `process_data`, carries only the server's own failures (listen, accept, and creating a client handle or the ping timer), which `init.lua` logs at error level [server/tcp.lua:M._handle_new_connection] [server/init.lua:M.start]
- A rejected handshake logs `Rejected client_<n>: <reason>` at warn level, with the reason from the body of the error response. Once the error response is written, `on_error` removes the client from the server and closes its socket [server/client.lua:M.process_data]
- Once a client is closing, `process_data` drops the bytes it sends, and `close_client` frees the unparsed bytes and the reads of an unfinished frame [server/client.lua:M.process_data] [server/client.lua:M.close_client]
- The server logs each error, warning, and info line from a libuv callback through `logger.one_line`, so the line never stops Neovim at "Press ENTER" [server/init.lua:M.start] [server/client.lua:M.process_data] [server/tcp.lua:M.start_ping_timer]
- Each connection gets the id `client_<n>`, where `n` counts the connections of this Neovim process in `_G.claudecode_clients_created`. An id never repeats, even after a reload of `claudecode.server.*`. A Claude CLI that reconnects gets a new id, so it does not own the diffs it opened before [server/client.lua:M.create_client]
- When the state is already `closing` or `closed`, `close_client` sends nothing [server/client.lua:M.close_client]
- A Close frame queued by `close_client` is followed by the close of the socket, from its write callback, so `client.close_pending` is set until then and `_remove_client` leaves the socket open. After a protocol error `process_data` calls `on_error` at once, so the client leaves `server.clients` and `on_disconnect` runs while the frame can still wait in libuv's queue behind the replies of a Claude that does not read. The ping timer cannot see that client, because it left `server.clients`, so `close_client` starts a deadline for the frame (`client.close_timer`, a repeating timer of `client.keepalive_timeout`). A socket that wrote no byte of its queue during a keepalive window is closed, and the queue with it, while a Claude that reads keeps its socket. The window starts with the frame, and one window without progress is enough here: the client is leaving anyway, so a close that comes too early after a blocked loop costs only its Close frame. The write callback and the deadline each close the socket if it is still open and end the other, so the first one to run wins, and a deadline never touches a socket that closed. A server without a ping timer has no keepalive window and its clients get no deadline, but `M.start` starts the timer in the same call that listens, before any client can connect. `drop_client` calls `abandon_close_frame`, so a client that the ping timer drops, for a keepalive timeout or a stalled write queue, has its socket closed at once [server/client.lua:M.close_client] [server/client.lua:fail_connection] [server/client.lua:start_close_timer] [server/tcp.lua:release_socket] [server/tcp.lua:drop_client]
- `sha1` rejects non-string input and input over 10 MiB [server/utils.lua:M.sha1]

## Side Effects

- `M.start` changes the global tool registry (`tools.setup`), opens a listening TCP handle, and starts a `vim.loop` ping timer [server/init.lua:M.start]
- When a client completed its WebSocket handshake (`on_open`, called from the 101 write callback in `client.lua`), the server schedules `claudecode.process_mention_queue(true)`. With an auth token it first logs `Authenticated WebSocket client connected` at debug level, because the handshake has checked the token by then. `on_connect` runs at the TCP accept, before the handshake and the token check, and only logs `WebSocket client connected, awaiting authentication` (`WebSocket client connected (no auth)` without a token) [server/init.lua:M.start] [server/client.lua:M.process_data]
- On disconnect, the server schedules `diff.close_diffs_for_client(client.id, "client disconnected")`, only when `package.loaded["claudecode.diff"]` is set and the client completed its handshake. A client without a completed handshake ran no tool, so it owns no diff. The cleanup runs through `utils.when_windows_allowed`: in the command-line window or under textlock it waits, and it runs once Neovim allows window changes again. One 50 ms timer checks for every waiting cleanup [server/init.lua:M.start] [lua/claudecode/utils.lua:M.when_windows_allowed]
- `M.stop` calls `diff.close_pending_diffs("server stopping")` when `package.loaded["claudecode.diff"]` is set, answers the requests in `M.state.in_flight`, resets `_G.claude_deferred_responses`, and clears `M.state.auth_token` [server/init.lua:M.stop]
- `M.start` logs only the auth token length, not the token [server/init.lua:M.start]
- `tools/call` debug lines name the tool and list the argument and result keys with their sizes (string bytes, table entry counts), never their values, so file contents and selected text stay out of `:messages`. An error result logs its code and message. A rejected call logs one line, `Rejected tools/call: <field> (<need>)`, and none of the others [server/init.lua:M.register_handlers]
- `client.create_client` increments `_G.claudecode_clients_created` [server/client.lua:M.create_client]
- `tcp.lua` seeds `math.randomseed` once per load of the module, on the first `port_iterator` call for a non-empty range, so a reload of `tcp.lua` seeds again. `init.lua` calls `math.random` at load. Both change the global PRNG [server/tcp.lua:ensure_rng_seeded] [server/tcp.lua:port_iterator]
- `client.process_data` writes handshake, PONG, and Close frames to the socket. It runs `on_message` and `on_close` through `vim.schedule`. It calls `on_error` directly after a failed handshake write or a written rejection, and after it queues the Close frame for a protocol error [server/client.lua:M.process_data] [server/client.lua:fail_connection]
- The ping timer writes ping frames. The check handle that each tick arms closes clients that timed out or stopped reading [server/tcp.lua:M.start_ping_timer] [server/tcp.lua:after_next_poll]
- Each tick that pinged a client creates one `vim.loop` check handle and one idle handle, and the judgement of every client of that tick, keepalive and stall, shares that pair. The check callback closes them, and `stop_server` closes those that did not run [server/tcp.lua:after_next_poll] [server/tcp.lua:M.stop_server]
- `close_client` starts a repeating `vim.loop` timer for the Close frame of a client that has `keepalive_timeout`. It runs until the frame is written, the socket closes, or the deadline closes the socket [server/client.lua:M.close_client] [server/client.lua:start_close_timer]
- `handshake.lua`, `frame.lua`, and `utils.lua` do no I/O [server/handshake.lua:M]
- `mock.lua` opens no sockets and keeps its clients and messages in its own `M.state` tables. Its `mcp.tool.invoke` handler calls the real `tools.handle_invoke`, which looks the tool up in the global registry. `mock.start` does not fill that registry. So in a fresh Neovim a simulated tool call returns `-32601` "Tool not found: <name>" and has no side effects. After `tools.setup` or the real server's `M.start` fills the registry, the call has that tool's real side effects (for example `saveDocument` writes the file) [server/mock.lua:M.register_handlers] [server/mock.lua:M.state] [tools/init.lua:M.handle_invoke] [tools/init.lua:M.setup]
