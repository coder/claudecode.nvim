# Check every tool call at the entry

The server checks the `params` of each `tools/call` request once, where the request enters, before a tool runs (#500). A malformed call gets JSON-RPC error `-32602` that names the wrong parameter. A valid call gets its normal answer. The probe sends the cases to the plugin server of one tree over a real WebSocket and judges each answer against one table. It also checks every text frame that the server sends for a Lua position (`.lua:` and a digit), the plugin's folder, the user's home folder and the temp dir of the run.

## Sub-features

- `call-params` answers `-32602` naming `params` when `params` is absent, `false`, `null`, `true`, a number, a string, `[]` or `[1]`. It names `name` for `{}`.
- `call-name` answers `-32602` naming `name` when `name` is `null`, `true`, `false`, a number, a list or an object.
- `call-arguments` answers `-32602` naming `arguments` when `arguments` is present and is not an object. A call with `arguments` absent or `{}` is a call without parameters.
- `call-string-param` answers `-32602` naming `filePath` when the `filePath` of `openFile` is not a string. `""` is a string, so `openFile` answers `-32000` `File not found: `.
- `call-normal` answers a valid `getWorkspaceFolders` call with the workspace folder: `name` `work`, `path`, `uri` and `rootPath` of the folder that nvim runs in.
- `call-no-leak` keeps every text frame that the server sends free of a Lua position (`.lua:` and a digit), the plugin tree path, a path under the real home folder and a path under the temp dir of the run, where nvim's `HOME`, the XDG folders, `TMPDIR`, `CLAUDE_CONFIG_DIR` and the lock file live. The work folder lies beside the temp dir, not in it, and a frame may hold it.

## How to get to it (user POV)

- The Claude CLI sends `tools/call` over the WebSocket. The user sees the tool error in Claude's reply, never a Lua path.

## Driving it with vcn.sh

Preconditions:

- Neovim 0.8 or newer and Node 22 or newer, which has a global `WebSocket` (the probe ran on Node 22.23.4 and 26.12.1). The script takes nvim from `VCN_NVIM`, else `mise which nvim`, else `PATH`, and node from `mise which node`, else `PATH`. It needs no `$V launch`, agent-tty or Chromium.
- A real nvim binary and a real node binary, not a version-manager shim: the script starts both with an empty environment, and a shim can fail to start that way. In a checkout that mise does not trust, `mise which nvim` fails and `PATH` can hold a shim. Then set `VCN_NVIM=<real nvim binary>`, for example `~/.local/share/mise/installs/neovim/0.12.3/bin/nvim`. The script exits 2 and names the binary that does not start. nvim must also be a direct child of the script: the Neovim binary itself, or a wrapper that runs it with `exec`. A wrapper that runs Neovim as a child makes nvim stop before the plugin starts, and the script exits 2 with a message that names the wrapper and says to set `VCN_NVIM` to the Neovim binary itself. Exit 2 also covers a temp dir or a work folder that cannot be made. When the server does not come up for another reason, it prints the last lines of nvim's output.
- No `claude` program on `PATH=/usr/bin:/bin`. The script exits 2 when it finds one.

Steps:

- **Whole proof.** Run `.agents/skills/verify-claudecode-nvim/scripts/proof-tools-call-wire.sh [tree]`. `tree` is a plugin tree with `lua/claudecode`, and defaults to this checkout. It prints one `ok: <case>` or `FAIL: <case>: <reason>` line per case and ends with `COUNT tools-call-wire cases=<n> failed=<n> leaks=<n>`. A pass is `failed=0 leaks=0` with at least one case, and exit 0. A failure exits 1, and its `FAIL` lines say what the case wanted and what came back. Exit 2 means the probe could not run, or that it judged fewer cases than the table holds (an empty table too). It prints no `COUNT` line then. A server that goes away during the run ends the probe at once with exit 2.
- **Red proof.** Run the probe against main from before #500: `dir=$(mktemp -d); git archive f932d7b6a91c71c3728257ae6284bf03f9d09c77 | tar -x -C "$dir"; .agents/skills/verify-claudecode-nvim/scripts/proof-tools-call-wire.sh "$dir"; echo "exit $?"; rm -rf "$dir"`. It prints `FAIL` lines, ends with `COUNT tools-call-wire cases=44 failed=30 leaks=15`, and `exit 1`.
- **Neovim 0.8.** Run the whole proof with `VCN_NVIM=<nvim of the v0.8.0 release>`. It prints the same lines as on 0.12.3.
- **Normalization and the leak rule.** `proof-tools-call-wire.mjs` reads every text frame that the server sends as the wire sent it, and no parse or rebuild comes first. It reads every escaped slash, a run of backslashes and a slash at any depth of nesting, as a slash. The path rewrite then applies to that text: the folder nvim runs in becomes `$CWD`, the temp dir (`/tmp/wire-probe.XXXXXX`) becomes `$RUN`, the tree becomes `$TREE` and the real home folder becomes `$HOME`, in that order. Each rewrite is plain text. The work folder is `work` in another temp dir, `/tmp/wire-probe-cwd.XXXXXX`, beside the temp dir and not in it. The two names differ after `wire-probe`, so neither path starts with the other, and no path under the temp dir can read as the work folder. The real home folder comes from the password database, because the checker starts with an empty environment. A frame leaks when its text then holds `.lua:` and a digit, `$RUN`, `$TREE` or `$HOME`, or holds 8 or more characters of the auth token in a row. The leak rule finds each of the four paths in a frame unchanged, so the probe refuses to run when the tree path, the work folder path, the temp dir path or the real home folder path holds a double quote, a backslash or a control character (the characters that JSON writes escaped). It exits 2 with a message that names the path, before it sends a case. (A backslash in the tree path or in the temp dir path can make nvim fail to load the plugin first: the script then exits 2 with `nvim wrote no lock file in 10 s`.) So a path in a sibling field, in an object key, in a nested list, in a duplicate key, or in a JSON fragment inside a plain string leaks. The leak rule also reads a frame that comes before the answer or within 200 ms after the last answer. It judges a frame that arrives after its own answer with the case in flight, so the case that is running when it arrives fails. A normal answer is compared with the answer written in the case table. The comparison reads a rebuilt copy of the answer that decodes a text item that holds JSON and rewrites its strings but not its keys, so two keys that the rewrite would make equal never pass as a correct answer.

## Gotchas

- The table holds `params`, `name`, `getWorkspaceFolders` and `openFile`. Another tool is not checked.
- The folder nvim runs in is not a leak, because `getWorkspaceFolders` returns it on purpose. The rewrite handles it first, so the answer passes even when that folder lies under the real home folder.
- When nvim and node are the binaries themselves, nvim starts with an empty environment apart from `PATH=/usr/bin:/bin`, `WIRE_PARENT`, `WIRE_TREE`, `WIRE_CWD`, and `HOME`, `TMPDIR`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, `XDG_CACHE_HOME` and `CLAUDE_CONFIG_DIR` in the temp dir. It runs with `terminal.provider = "none"`. The checker starts with no variable (a version-manager shim that does start adds variables of its own), so no variable of the caller, such as `NODE_OPTIONS`, reaches the process that holds the token. nvim and the checker leave nothing outside the two temp dirs, not even nvim's own temp root (`mise which node`, which the script runs, can write files under the caller's home). The script stops nvim and the client by PID and removes its temp dir `/tmp/wire-probe.XXXXXX` and the temp dir of its work folder `/tmp/wire-probe-cwd.XXXXXX` on every end that bash can trap (a normal exit, a failed case, TERM, INT and HUP), unless a signal cuts that cleanup short (the next bullet but one says what stays then).
- The auth token lives in the memory of nvim and of the checker, and in the `0600` lock file in that temp dir. The checker sends it only in the upgrade header. The checker prints only text that it wrote itself and text of a frame, and it prints a frame's text only when it holds no run of 8 or more characters of the token (otherwise the output says `<holds the auth token>`). It never prints the message or the stack of an exception that Node or a library raised, because such a message can quote its input. A frame that is not JSON and a lock file that does not parse each end the run with exit 2 and a fixed message. Any other exception ends the run with exit 2 and one line that holds only the exception's class name. nvim's output file holds no token. The script prints the last five lines of nvim's output only while no lock file exists, so it holds no token that it could filter out of them. Those lines come from the tree under test, and the plugin logs only the length of its token. A tree that prints its own token there has a defect of its own, which the probe shows.
- When the script ends and nvim is still alive, nvim and the checker end and the lock file is gone within 5 seconds, as long as nvim's main loop runs. nvim is a direct child of the script, checks its parent every half second and, when the parent is gone, stops its server, which removes the lock file and closes the socket that ends the checker. The cleanup above is the faster path. When it does not run (SIGKILL of the script) or a signal cuts it short, the temp dirs can stay. The bound needs nvim's main loop to run: a tree under test that blocks it, together with a SIGKILL of the script, is outside the bound. A SIGKILL to the whole process group kills nvim too, so nothing deletes the lock file: it then holds the token of a server that no longer runs, in the `0700` temp dir. From the first TERM, INT or HUP that the script handles, and from the first command of its cleanup, further TERM, INT and HUP are ignored.
- The leak check catches a path that the plugin puts into a text frame by accident: the plugin writes every text frame (each JSON-RPC message) with `vim.json.encode`. The check does not read Ping, Pong and Close frames: the checker's WebSocket client passes no Ping or Pong to it, and the checker ignores the code and reason of a Close. It does not promise to catch a server that hides a leak on purpose. It looks for the tree path as the script resolved it, for the home path as the password database gives it and for a path under the temp dir: another spelling of one (the other name of a symlink, a relative path, `~`) is outside the check, and a Lua position (`.lua:` and a digit) is found in any spelling. nvim runs with `HOME`, the XDG folders, `TMPDIR` and `CLAUDE_CONFIG_DIR` inside the temp dir, and the lock file is in it, so the check finds a path that the plugin builds from them (`vim.fn.expand("~")`, `vim.env.HOME`, the lock file path, a `stdpath()` path except `config_dirs` and `data_dirs`, which are system folders). When the password database gives `/` as the home folder, the home check is off, because the checker keeps a path only when it is longer than one character. It relies on `vim.json.encode` writing `"` and `\` escaped on Neovim 0.8 and 0.12, `/` escaped on 0.8 only, and no other printable ASCII character.
- Only nvim, the checker and the user who runs the probe can read the auth token, and root, who can read any file and any process's memory: that is inside the trust boundary by design. The two temp dirs come from `mktemp -d`, each with mode `0700` and a fresh name, and the script uses only the path that `mktemp` printed (resolved with `pwd -P`). The token is in no process's arguments or environment, in no file outside the temp dir and in no kept log. The probe trusts the code that the caller picks to run. That includes the tree under test, the nvim binary (from `VCN_NVIM`, mise or `PATH`), the node binary (from mise or `PATH`), and the helper commands that the script finds on the caller's `PATH` (`env`, `mktemp` and `rm`, for example). mise and `PATH` find those programs through the caller's environment, so the folders that they search, `HOME` included, are part of what the caller picks. All of it runs as the caller, who can read the token, so a tree or a program that copies the token to another place is outside this promise. The caller's `TMPDIR`, `HOME`, umask and `CLAUDE_CONFIG_DIR` do not move the lock file or change its mode: the script sets umask 077, and nvim gets its own `TMPDIR`, `HOME` and `CLAUDE_CONFIG_DIR` in the temp dir.
- A case with no answer in 3 seconds fails with `no answer in 3 s`.
