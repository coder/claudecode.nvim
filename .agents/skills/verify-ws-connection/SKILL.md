# Verify the WebSocket connection lifecycle

Claude Code talks to the plugin over one WebSocket connection. The plugin must not run a request from a Claude that is gone, must report each disconnect once, must tell Claude why it closes, must not drop a Claude that answers its pings, and must not keep a dead connection or its socket forever. This check explores every order of Claude's frames, hang-ups and stalls, libuv read and write callbacks, ping-timer ticks, scheduled callbacks and server stops in a small model of one connection, with each guard switched on or off to match the code as it is now.

## Rules

| Rule                     | Plain sentence                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Harm when broken                                                                                                                                   |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NoRequestAfterEnd`      | A request from Claude runs only after its 101 reply was written, and never after the plugin started to close the connection or saw it end.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | A request from a Claude that hung up or closed still changes the editor (opens a diff, moves the cursor), and its answer goes nowhere.             |
| `DisconnectReportedOnce` | `on_disconnect` runs at most once per client.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | The disconnect cleanup (closing that client's pending diffs) runs twice.                                                                           |
| `StatusCloseDelivered`   | A Close frame for a protocol error (1002, 1003, 1007, 1009) or a server stop (1001) is written before the plugin closes the socket, as long as Claude keeps reading. A Claude whose queue makes no progress for one keepalive window loses the frame to the deadline of `close_client`, which closes the socket (not modeled).                                                                                                                                                                                                                                                                                                                                                                                                                               | Claude cannot tell a protocol error or a shutdown from a crash: the connection just drops.                                                         |
| `NoFalseTimeout`         | A Claude that answers each ping before the next tick is never dropped by the ping timer, whatever blocks Neovim or sleeps the machine. A tick only pings and stamps the oldest unanswered ping. The check that drops a client runs after a poll that read the sockets. It judges nothing when its poll came more than 1.5 intervals after its tick, and any bytes the plugin reads from the client clear the stamp. A Claude that stopped once is not covered, and neither is a pong that comes later than one interval: with an unrelated read callback that blocks inside the poll phase and refreshes the loop time, the code closes that client once its ping is 2.5 intervals old (the model has no step for it). A real Claude answers a ping at once. | A Claude that answers each ping before the next tick is disconnected with 1011.                                                                    |
| `DeadClientDropped`      | A client whose Claude hung up or stopped answering, or whose connection the plugin started to close, eventually leaves `server.clients` with its `on_disconnect`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | The plugin keeps counting Claude as connected (`is_claude_connected()`), keeps the unsent writes in memory, and never runs the disconnect cleanup. |
| `DroppedSocketCloses`    | Once a client left `server.clients`, or the server stopped, its socket eventually closes, as long as Claude reads again.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | The socket stays open, in `CLOSE_WAIT` once Claude hangs up, until Neovim exits: one leaked file descriptor each time.                             |

`DeadClientDropped` and `DroppedSocketCloses` are liveness rules ("eventually"). The others hold in every state. TLC reports only the first broken invariant of a run, and a `NoFalseTimeout` break is shorter than any other break, so `check.sh` checks `NoFalseTimeout` in a run of its own (`live-NoFalseTimeout`, written as `[](~falseTimeout)`). A new break of the other three then still shows in the `main` run.

## Run

```bash
.agents/skills/verify-ws-connection/check.sh            # 2 to 6 min, 4 min at a host load average of 16
.agents/skills/verify-ws-connection/check.sh --keep     # same, keeps the TLC configs and output, prints the dir
.agents/skills/verify-ws-connection/check.sh --mutants  # about 80 min at a load average of 14, after you edit the model or a fact
.agents/skills/verify-ws-connection/check.sh --record   # rewrite covered.lock, only after "Update after an intended change" (refused together with --mutants)
.agents/skills/verify-ws-connection/check.sh --hash-only  # 2 to 30 s, no TLC: only compares covered.lock with the code (exit 0 fresh, 2 error, 3 stale)
```

The shared harness `scripts/tla/check-lib.sh` does the work. Its header lists what `check.sh` sets. CI's `covered-lock` job runs every `.agents/skills/verify-*/check.sh` on each pull request, with the TLC jar cached. `Required` does not need that job. On the code as written this check passes, so a broken rule or `STALE` in that job's log for this check is news.

Needs bash 4 or newer, Java 11 or newer (`JAVA=/path/to/java` overrides), `sha256sum` or `shasum`, and curl for the first run, which downloads TLC 1.7.4 to `~/.cache/claudecode-nvim-tla/` and refuses a jar whose sha256 differs. Run one copy at a time on a shared host: TLC is CPU heavy.

Exit codes:

- `0` is PASS.
- `1` means a rule broke.
- `2` is a tool or script error, or a model whose `TypeOK` breaks.
- `3` is STALE. The covered code changed since the model was last confirmed, so the change is unverified.

## Does the change touch the verified code?

Run `check.sh --hash-only`. `covered.lock` records a hash of each covered file: `server/client.lua`, `server/tcp.lua`, `server/handshake.lua`, `server/init.lua` and `init.lua`. Any change to one of them reads `STALE` (exit 3) until someone confirms that the model still describes the code. `git log -1 -- .agents/skills/verify-ws-connection/covered.lock` gives the sync commit: the last commit at which someone confirmed the model against the code. Move it forward only by `check.sh --record`, after "Update after an intended change".

To show where to look, the record also hashes each block the model describes and lists every non-comment line that changes a client's state, writes to or closes its socket, or adds, drops, stops or times out a client, with its enclosing top-level statement. The STALE output prints a `was:`/`now:` pair per changed file, block or line. Covered blocks:

- In `server/client.lua`: `create_client`, `add_data_frame`, `fail_connection`, `process_data` (handshake, 101 write callback, frames, Close, PONG, the scheduled `on_message` guard), `send_message`, `send_ping`, `close_client`, `abandon_close_frame`.
- In `server/tcp.lua`: `_handle_new_connection` (accept, `read_start`, EOF and read errors), `release_socket`, `_disconnect_client`, `_remove_client`, `stop_server`, `after_next_poll` (the libuv check and idle handles that run a callback after the next poll), `judge_silence` (the keepalive judgement), `drop_client`, `start_ping_timer`.
- In `server/handshake.lua`: `process_handshake`, `extract_http_request`.
- In `server/init.lua`: `M.start` (the callbacks and the ping timer), `M.stop`.
- In `init.lua`: `M.start`, `M.stop` (`:ClaudeCodeStop` and `VimLeavePre` call it).

A changed file with no changed block or line still needs a look, for example a new caller of `close_client` in another function. A PASS says the model holds for the guards the facts read, on code that matches the record. It does not review a change. STALE never means "probably fine".

When two branches change the same covered file, `covered.lock` conflicts. Merge `origin/main`, follow "Update after an intended change" on the merged code, run `check.sh --record`, and commit the merge with the new `covered.lock`.

## Read the result

`check.sh` prints the code facts first. Each fact is a guard that a regex reads from the source. `TRUE` means the regex found the guard. `FALSE` means the model runs without that guard. A `FALSE` you did not expect is either a removed guard (a bug) or a guard reworded past the regex (a modeling error). A fact reads lines in order, not the structure of the code, so a guard that moves to a place where it no longer guards can still read `TRUE`. The verifiers found three such moves (the `end` of the `DispatchGuard` if above `on_message`, and `abandon_close_frame` with `release_socket` or `drop_client` in the `stop_server` loop). The facts read them now, and the unit tests in `gone_client_spec.lua` and `connection_lifecycle_spec.lua` catch each of them.

On `BROKEN`, the script prints the TLC trace as action names. Each action of `model/WsConnection.tla` names the file and function it models. Read the trace with the pstack `/statechart` skill:

1. Rerun with `--keep`.
2. Copy the broken run's `.cfg` from the kept dir. Lower `PeerBudget` to 1 (only the upgrade request), then raise it one frame at a time, only until the rule breaks again. Set `MaxSleeps` to 0 unless the path needs a delayed tick (a gap, a stale tick, or a sleep between a tick and its poll: each uses up one of the `MaxSleeps`). Stop at the smallest config that still breaks the rule.
3. Give `/statechart` the kept `WsConnection.tla`, that cfg, and the view `model/statechart-view.ts`. Delete the kept dir when you are done.

The report tells the path in plain words, for example "Claude connects, the ping timer ticks four times while Claude answers each ping and the plugin reads none, then the ping timer drops Claude for no reply". That is the `NoFalseTimeout` finding below.

Then decide which kind of failure it is:

- **Real bug.** A fact went `FALSE` because the change removed or moved a guard, or a fixed finding's path is open again, and the code can take the path. Replay it on the real code (see `replays/`) before you report it, and report it in the code's words. Never weaken a rule or the model to make it pass.
- **Modeling error.** The facts are `TRUE` but the path needs a step the code cannot take, or a fact reads `FALSE` because the guard was reworded and still works (for example `if not (client.state == "connected") or ...`). Fix the regex or the model, run `--mutants`, and say what you changed.

`--mutants` removes each guard alone and checks each rule alone: each fact must break the rule its `EXPECT` entry names, and each rule must break at least once. One guard is the exception. `RejectClosesSocket` alone breaks no rule, because `_disconnect_client` also closes the socket of a client that left the server, so `--mutants` removes it together with `UnlistedDisconnectReleases`. The environment steps of the bugs this model found (`WindowFullOnProtocolClose`, `StopBeforeOnClose`, `StaleLoopTime`, `PollMissesPong` and `SleepInWindow` in the model) stay on in every run.

## Bugs this model found

The first run of this model broke three rules on the code as it was. Each one was replayed on the real code, and PR #455 fixed all three. Reviews of this skill's own PR then found more false timeouts that the first model could not see. PR #479 and PR #488 fixed them, in four rounds (the last three from reviews), and the model describes the final design of #488.

- **`NoFalseTimeout`.** The ping timer's wake reset touched only `connected` clients, so a Neovim main loop that blocked for more than `interval * 1.5` between the accept and the handshake left the new client with the `last_pong` that `create_client` set at the accept. The timer then dropped a Claude that answered every ping, one interval after its handshake, before any ping reached it. PR #455 made the 101 write callback set `last_pong`. Since #488 a client has no stamp until a tick pings it, so no block between the accept and the handshake can time it out, and the model needs no guard for it.
- **`DeadClientDropped`.** After a protocol error `close_client` queued its Close frame and left `on_error` to the write callback, which runs only once Claude reads again. A Claude with a full receive window kept its client in `server.clients`, `is_claude_connected()` returned `true`, and `on_disconnect` (the diff cleanup) did not run. `process_data` now reports the client at once (`ProtocolReportsAtOnce`). `client.close_pending` keeps `_remove_client` from closing the socket while the Close frame waits, so the frame is still delivered (`CloseWriteOwnsSocket`).
- **`DroppedSocketCloses`.** A server that stopped after Claude's Close frame was read and before the scheduled `on_close` ran dropped the client from `server.clients`, and nothing closed its socket: it stayed in `CLOSE_WAIT`. `_disconnect_client` now closes the socket of a client that is no longer listed (`UnlistedDisconnectReleases`).
- **`NoFalseTimeout`, again (#479).** A tick that Neovim ran late after a block of 1.0 to 1.5 intervals is below the wake threshold (`interval * 1.5`), so `last_pong` was not reset, and the tick can run before the plugin reads Claude's pong. libuv runs timers before it reads sockets. With libuv 1.44, which Neovim 0.8 bundles, that holds after a block in any callback. With newer libuv it holds after a block in a check callback or an I/O read callback, and not after a block in `vim.schedule` or a timer callback, which read the socket first. The tick found the last pong 2.3 intervals old and dropped a Claude that answers every ping. PR #479 pinged again at the first tick that found no pong, and dropped at the second.
- **`NoFalseTimeout`, a third time (#488).** libuv 1.44 runs the timers at the end of a pass of the main loop, after the check handles, and again at the start of the next pass. Neovim runs `vim.schedule` callbacks between the two. A tick at the end of one pass, a block in `vim.schedule`, and a tick at the start of the next ran with no read of Claude's socket between them, and the second tick of #479 dropped a Claude that answered every ping (`replays/two-blocks-before-read.lua`). Any number of ticks can run before a read, so no counter of ticks fixes it. A tick now only pings, and stamps the oldest unanswered ping. The callback of a libuv check handle, which libuv runs after the poll phase that reads the sockets, drops the client whose stamp is two and a half intervals old (`JudgesAfterRead`, `StampKeepsOldestPing`, `WakeClearsStamp`). The model needs no step for a late tick, because its ticks already run at any point between reads. With `JudgesAfterRead` off, `NoFalseTimeout` breaks after a connect, a handshake, and four ticks that Claude answers one by one with no read between them. `StaleLoopTime` is the step for a stamp from the loop time that libuv cached before an earlier callback of the pass blocked.
- **`NoFalseTimeout`, a fourth time (the review of #488).** The check can still run on a poll that does not reach Claude's answer, in two ways. First, Claude writes while Neovim is blocked, and a pong can wait behind more unread data than the socket holds: one poll reads the first part of a large message and stops (`PollMissesPong`). With only a PONG clearing the stamp, `NoFalseTimeout` breaks in the model, and a replay drops Claude after a block of 1.4 intervals twice in a row. The read callback now clears the stamp on any bytes (`BytesClearStamp`): Claude shows it is alive by writing anything. Second, the machine sleeps between a tick and the poll before its check (`SleepInWindow`): Neovim and Claude stop together, the loop time jumps, and Claude answers only after the poll, so no bytes arrive. The check now judges nothing when its poll came more than `interval * 1.5` after its tick (`GapSkip`), and the next tick sees the gap and clears the stamps, as for any wake. Each of the two guards alone leaves one of the two paths open.
- **`NoFalseTimeout`, a fifth time (Codex's review of #488).** The tick read `vim.loop.now()` before it called `vim.loop.update_time()`. libuv runs all timers of a pass with the loop time of the start of the pass, so when an earlier timer callback of the pass blocked for longer than `interval * 1.5`, or the machine slept in it, the tick saw no gap. It kept the stamps of the pings from before the sleep. The check after the poll, which comes right after the tick, then saw a small gap between the tick and the poll and a very old stamp, and dropped a Claude that had no time to answer. The tick now calls `update_time()` first (`ClockFreshAtTick`), sees the wake, and clears the stamps. In the model a `stale` tick is a wake that only a tick with a fresh clock sees (`StaleLoopTime`): with `ClockFreshAtTick` off, `NoFalseTimeout` breaks. There is no replay of this one, because a replay cannot make a timer callback run before the ping timer inside one pass. Two unit tests pin the fix. `ages a ping from when it was sent, though a callback of the pass blocked for half an interval before` turns red when the tick has no `update_time()` and when it comes after `local now = vim.loop.now()` (the stamp and the wake test then read the old time). `takes a tick for a wake when a callback before it in the pass blocked, though the loop time is old` turns red only when `update_time()` comes after the wake test and `now` is read again after it (the stamp is fresh and the wake test saw the old time).

## Update after an intended change

1. Read every `was:`/`now:` line of the STALE output and the code behind it.
   - If only `file` lines changed, and the change cannot reach a client's state, its socket, `server.clients`, the ping timer or the server stop (for example a terminal or diff change in `init.lua`), say so in the PR. Then skip to step 4.
2. If the behavior changed, change the action in `model/WsConnection.tla` that cites that code. If a guard moved, change its fact regex in `check.sh`. If a guard is new, add a fact and its `EXPECT` entry.
3. Run `check.sh --mutants`. Every fact must be caught by its rule, and every rule must break at least once.
4. Run `check.sh` and read the result.
5. Run `check.sh --record` only once you have confirmed that the model describes the code at this commit. Commit `covered.lock` with the change.

## Scope and bounds

- One connection. Clients share only `server.clients` and the loops of the ping timer and `stop_server`, which treat each client alone. Client ids, the diffs a client owns, and the answers to its `openDiff` calls are checked by `verify-diff-lifecycle`.
- The safety rules run with Claude sending 3 frames, its upgrade request included (pongs and the hang-up come on top), and two delayed ticks (a gap above 1.5 intervals, a stale tick, or a sleep between a tick and its poll): 262,285 states in the joint run and 256,264 in the `NoFalseTimeout` run. The liveness rules run with 2 frames and no delayed tick: 11,701 states each.
- Writes follow libuv. A write goes into the kernel at once when nothing waits in libuv's queue and Claude's window has room. Its callback runs in a later step. Claude's window fills only when the plugin sends a large message while Claude does not read (`PluginSendsLarge`). When Claude reads again, libuv writes the whole queue in one step: the short gap between Claude making room and libuv's next write is not modeled. `uv_close` cancels what waits in the queue and runs the pending callbacks when the close finishes.
- One read carries one frame. `process_data` stops after a Close frame or a protocol error, and drops the bytes of a closing client, so a read of several frames reaches no other state.
- Every plugin step (reads, write callbacks, closes, scheduled callbacks, timer ticks, the poll with its check handles) is fair. Claude is never assumed to act. `DroppedSocketCloses` alone assumes that Claude reads again (`PeerEventuallyReads`). `NoFalseTimeout` alone assumes that a Claude that reads answers each ping before the next tick (`PeerAnswersBeforeTick`), except before a tick after a gap, because the machine slept with Claude. Delayed ticks (a gap, a stale tick) are bounded (`MaxSleeps`), so the timer cannot skip forever.
- Ticks and reads interleave freely: a tick can run before the read of a pong that is already in the socket, however many ticks run in a row. libuv allows fewer orders (two ticks with no read between them), so the model covers every real one. The poll reads every frame that reached the socket before it, or, with `PollMissesPong`, only the first frame of each client. It does not read what Claude sends after it, such as the answer to the ping of the same tick. The poll and the check handles after it are one step of the model. The other callbacks of that pass of the loop (write callbacks, closes) run before or after it.
- Time counts in ticks. A stamp is `Limit` ticks old at the third tick after it. Ticks on time are one interval apart, so `interval * 2.5` is reached 3 intervals after the first unanswered ping. One late tick delays it. Two late ticks in a row, or a poll that a block delays after a tick, can reach it as early as 2.5 intervals, and a tick more than 1.5 intervals after the one before it is a wake that restarts the count. The model does not count the length of a block. `MachineSleeps` stands for a block or a sleep longer than the gap: it marks the loop time as jumped, the next poll's check judges nothing, and the next tick is a wake. Why `2.5` and not `2`: a limit of whole intervals meets the 1 ms resolution of the loop time at exactly the boundary, and the half interval keeps timer jitter from moving the drop. `NoFalseTimeout` holds for any limit above `interval * 1.5`, the window in which a check still judges: the poll that precedes the check reads the pong, and a block inside the poll phase can add at most that much age. A limit of 1.0 to 1.5 intervals passes the model, and real Neovim still drops a Claude that answered in 30 to 100 ms when a read callback blocks about 1.3 intervals in the poll after the tick and refreshes the loop time (the model counts that block as one tick, and a tick as a whole interval). The limit sets how long a silent Claude lives, and how slow an answer can be.
- Not in the rules, on purpose:
  - The keepalive Close frame (1011). A Claude whose window is full never gets it, because `_disconnect_client` closes the socket right after `close_client` queues it. `server/README.md` documents it. Claude sees its connection end without a status, and the log shows `Closed client_<n>: no reply for <s>s`.
  - The reply to Claude's Close frame. The code makes no promise about it, and it is lost the same way when Claude's window is full: Claude sees the connection end without the reply.
  - A connection that never finishes its handshake. The ping timer checks only `connected` clients, so a TCP connection that never sends its upgrade request stays in `server.clients` until it hangs up. The user sees nothing: `is_claude_connected()` counts handshaken clients. No code or doc promises otherwise.
  - A client that writes data but never answers a ping. Any bytes clear the stamp, so the ping timer keeps it: it is alive, and the plugin does not judge what it writes. A real Claude answers each ping it reads, so this is a stalled or foreign process. The user sees it as connected (`is_claude_connected()` is true) until it stops reading or hangs up. Before #488 the ping timer dropped it.
  - The stall rule of #467 (`judge_stall`), and a client that sends bytes and never reads its socket. Its bytes clear the stamp, so the keepalive never drops it, and the plugin keeps counting it as connected: every message for it waits in libuv's queue, in Neovim's memory. The stall rule runs in the same callback as the keepalive, for a client that answers its pings. It closes a client whose write queue makes no progress at two ticks in a row with 1011 "Not reading", `on_disconnect` gets 1006 "Write queue stalled", and the log shows `Closed client_<n>: not reading for <s>s, <n> KB queued`. Until the kernel's socket buffers are full every write completes and an empty queue counts as progress, so the close comes later than that. The model has no queue size, so it checks the keepalive judgement only.
  - The deadline of a Close frame (`start_close_timer` in `close_client`): a socket whose Close frame stays queued for one keepalive window with no progress is closed, and the queue with it. A Claude that never reads cannot hold the socket for good either. The user sees nothing in the log: Claude sees its connection end without the 1001, 1002, 1003, 1007 or 1009 status. The model does not describe the deadline, and keeps its weaker assumption that Claude reads again (`PeerEventuallyReads`).
- Not modeled, with what a user sees if the code gets it wrong:
  - Frame encoding and parsing (`server/frame.lua`, unit tests): Claude disconnects with a protocol status (1002, 1003, 1007, 1009), or a request fails to decode (JSON-RPC error -32700).
  - Fragmented messages: a request in several frames never runs, or the connection closes with 1007.
  - Claude's own pings (the PONG reply is a write with no callback): Claude's ping gets no pong, and Claude can treat the connection as dead.
  - The HTTP checks of `handshake.lua` (the model only knows "accepted" or "rejected"): a valid Claude is refused (`Rejected client_<n>: <reason>` at warn level), or a client without the right token is accepted.
  - Deferred responses and diffs (`verify-diff-lifecycle`): a diff stays open, or a tool call gets no answer.
  - The mention queue that `on_open` starts once a client's handshake completed (it only schedules `process_mention_queue`, and touches no client, socket or timer): an `@` mention reaches Claude late, or the plugin reports a connection timeout and drops the queue.
  - The lock file: Claude Code finds no running IDE and does not connect.
  - Port selection: `:ClaudeCodeStart` reports `No available ports in range <min>-<max>`.
  - A restart (old clients keep the old server object, whose `clients` table is empty): a scheduled callback of the old server finds no client and does nothing.
  - Two servers in one Neovim: the plugin starts one server per Neovim.
- Not facts: the closing checks at the top of `process_data` and in its frame loop. Removing one alone breaks no rule, because `DispatchGuard` and `DisconnectOnce` also stop what follows. The checks in the keepalive check callback (`server.clients[client.id] == client` and `client.state == "connected"`) are not facts either: `close_client` and `_disconnect_client` already do nothing for a client that left or is closing, so a check without them differs only by an info line in the log. `drop_client` also calls `abandon_close_frame`, which does nothing for a stamped client: a stamped client has no pending protocol or stop Close frame.
