# Verify the Claude terminal lifecycle

You open Claude in a Neovim terminal, hide it, show it, send it context, and close it. Claude can exit on its own. The plugin can reload while Claude runs (`:Lazy reload`). The plugin must run one Claude at a time, stop it when you close it, show a running Claude when you open it, and touch only its own window. This check explores every order of your commands, Claude's exits, the plugin's scheduled callbacks, autocmds that call the plugin during a start, and one module reload (with a possible change of provider) in a small model. Each guard is switched on or off to match the code as it is now.

## Rules

| Rule                        | Plain sentence                                                                                                     | Harm when broken                                                                                        |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| `AtMostOneClaude`           | At most one Claude runs, apart from the one a close is stopping.                                                   | Two Claude sessions connect to Neovim. One of them is untracked, so no command reaches it.              |
| `CloseStopsClaude`          | When `:ClaudeCodeClose` returns, no Claude that ran when it began still runs.                                      | You close Claude and it keeps running in a buffer you cannot see.                                       |
| `CloseNeverReuses`          | The plugin never tracks again a terminal it began to close.                                                        | An open during the close's wait gets the terminal that is being deleted, and you end up with no Claude. |
| `OpenShowsLiveClaude`       | After an open, a show or a focus, you see a running Claude. A snacks terminal with `auto_close = false` is exempt. | You get `[Process exited]` or your own file instead of Claude, and a queued at-mention times out.       |
| `HideKeepsClaude`           | Hiding Claude's window keeps Claude running.                                                                       | A toggle ends the Claude session and loses the conversation.                                            |
| `HideNoError`               | Hiding Claude's window raises no error, also while a start runs.                                                   | `:ClaudeCode` prints an `E5108`/`E444` or `Invalid window id` error trace and does nothing.             |
| `FailedStartLeavesNoWindow` | A failed start leaves no window, no buffer and no tracked terminal.                                                | A broken `terminal_cmd` leaves an empty split, and the next open reuses a terminal with no job.         |
| `ExitClosesOnlyOwnWindow`   | With `auto_close`, Claude's exit closes only Claude's own window, and never the last window.                       | The plugin closes a window where you edit a file, or raises `E444` from a scheduled callback.           |

`OpenShowsLiveClaude` exempts snacks with `auto_close = false` on purpose. `lua/claudecode/terminal/README.md` documents that snacks reuses the tracked instance while `terminal:buf_valid()` is true, and registers its `TermClose` handler only with `auto_close`. So an open after Claude exited shows the exited terminal again. The native provider starts a new Claude in that case.

## Run

```bash
.agents/skills/verify-terminal-lifecycle/check.sh            # about 1 min
.agents/skills/verify-terminal-lifecycle/check.sh --keep     # same, keeps the TLC configs and output, prints the dir
.agents/skills/verify-terminal-lifecycle/check.sh --mutants  # about 15 min, after you edit the model or a fact
.agents/skills/verify-terminal-lifecycle/check.sh --record   # rewrite covered.lock, only after "Update after an intended change" (refused together with --mutants)
.agents/skills/verify-terminal-lifecycle/check.sh --hash-only  # about 10 s, no TLC: compares covered.lock with the code (exit 0 or 3)
```

The script sources `scripts/tla/check-lib.sh`, which pins TLC 1.7.4 by sha256 and downloads it to `~/.cache/claudecode-nvim-tla/` on the first run. It needs bash 4 or newer, Java 11 or newer (`JAVA=/path/to/java` overrides `java` on PATH), `sha256sum` or `shasum`, and curl for that first download. Run one copy at a time on a shared host. TLC is CPU heavy. CI runs every `.agents/skills/verify-*/check.sh` in the `covered-lock` job on every pull request.

Exit codes:

- `0` is PASS.
- `1` means a rule broke.
- `2` is a tool or script error, or a model whose `TypeOK` breaks.
- `3` is STALE. The covered code changed since the model was last confirmed, so the change is unverified.

## Does the change touch the verified code?

Run the check. `covered.lock` records a hash of each covered file: `lua/claudecode/terminal.lua`, `lua/claudecode/terminal/native.lua`, `lua/claudecode/terminal/snacks.lua`, `lua/claudecode/terminal/owned.lua` and `lua/claudecode/init.lua`. Any change to one of them reads `STALE` (exit 3) until someone confirms that the model still describes the code. `init.lua` is covered because the model's steps are its `:ClaudeCode`, `:ClaudeCodeFocus`, `:ClaudeCodeOpen` and `:ClaudeCodeClose` commands and `send_at_mention`. `terminal/external.lua` and `terminal/none.lua` are not modeled and not covered.

The record also hashes each block the model describes, and lists every non-comment line of the covered files that touches the tracked terminal (`OWNED_MARK`, `cleanup_state(`, `forget_exited_job`, `forget_ended_terminal`, `adopt_existing_terminal`, `wrap_terminal`, `upgrade_wrapper`, `remember_backdrop`, `register_window_events`, `adopted_config`, `focus_adopted`, `stop_snacks_terminal`, `stop_native_terminal`, `stop_other`, `stop_buffer`, `open_terminal(`, `close_terminal(`, `hide_terminal(`, `show_hidden_terminal(`, `cc_hide(`, `cc_show(`, an assignment to `terminal`, `termopen`, `jobstop`, `vim.wait(`, `nvim_win_close`, `get_provider()`, `load_provider(`, or a `terminal.open/close/simple_toggle/focus_toggle/ensure_visible(` call), with its enclosing top-level statement. The STALE output prints a `was:`/`now:` pair per changed file, block or line.

Covered blocks:

- In `terminal.lua`: `load_provider`, `get_provider`, `ensure_terminal_visible_no_focus`, `M.open`, `M.close`, `M.simple_toggle`, `M.focus_toggle`, `M.hide_float`.

## Read the result

`check.sh` prints the code facts first. Each fact is a guard that a regex reads from the source. `TRUE` means the regex found the guard. `FALSE` means the model runs without that guard. On a healthy tree every fact is `TRUE`. A `FALSE` is either a removed guard (a bug) or a guard reworded past the regex (a modeling error). See below for how to tell them apart.

## Update after an intended change

1. Read every `was:`/`now:` line of the STALE output and the code behind it.
   - If only `file` lines changed, and the change cannot reach the terminal's start, show, hide, close, exit handling, adoption or provider choice (for example a diff or selection change in `init.lua`), say so in the PR. Then skip to step 4.
2. If the behavior changed, change the step in `model/TerminalLifecycle.tla` that cites that code. If a guard moved, change its fact regex in `check.sh`. If the change adds a guard, add a fact, an `EXPECT` entry for the rule that must break without it, and a mutant branch in `tla_constants`.
3. Run `check.sh --mutants`. Every fact must be caught by its rule, and every rule must break at least once.
4. Run `check.sh` and read the result. If a rule breaks, replay the path (see Replays) and fix the code before you record.
5. Run `check.sh --record` only once you have confirmed that the model describes the code at this commit. Commit `covered.lock` with the change.

## Scope and bounds

- The main run uses two terminals (`Terms = {t1, t2}`), the providers `"native"` and `"auto"` (`"snacks"` resolves the same way in `get_provider`, plus a warning when it falls back), snacks.nvim loadable or not at setup, and `auto_close` true or false. Your `'hidden'` option is chosen only when the code does not set `bufhidden=hide`, because it changes nothing otherwise. Every environment switch is on: one reload that can also change the provider, one autocmd open per start, opens while callbacks are queued, `:e` in Claude's window, `:bwipeout!` of Claude's buffer, and `:only`. TLC stops exploring past a broken rule (`CONSTRAINT AllRulesHold`), which is enough because it stops at the first one anyway. With no rule broken the run explores 263,060 distinct states.
- A mutant run keeps only its guard's provider and the switches the guard needs (`tla_constants` in `check.sh`), so another switch cannot break the mutant's rule first. Each fact has an `EXPECT` entry. A guard that another guard covers for is removed together with it, as a pair. `OwnedLiveNeedsMark` and `NativeExitClearsMark` or `NativeCloseClearsMark` pair with `OwnedLiveSkipsEndedJob`, because the job check alone also rejects the terminal. `NativeAdoptedExitHandled` pairs with `NativeEntriesForgetEndedJob`, and `SnacksExitForgets` with `SnacksEntriesForgetEndedJob`, because an entry runs the exit cleanup itself. `NativeExitForgetsOwnJobOnly` pairs with `NativeCloseAdopts`, and `SnacksForgetChecksInstance` with `SnacksCloseAdopts`, because a close adopts a Claude that a stray cleanup left untracked. `SnacksAvailabilityCached` pairs with `SnacksStopsNativeClaude`, because a snacks start stops the native Claude that a provider switch would leave running.
- One step is one run of Neovim's main loop. `vim.wait` in a close lets job exits, scheduled callbacks and a scheduled open run, and typed commands not. Neovim fires `TermClose` while it handles the exit and queues `on_exit` after it, so a callback that a `TermClose` autocmd schedules runs before the one `on_exit` schedules (`native-open-after-exit.lua` relies on this and shows it).
- A diff that opens in a float's tab hides a visible float through `terminal.hide_float(tab)` (#447, and #504 for the tab check). `M.hide_float` of `snacks` runs `cc_hide` on the tracked terminal, which is the model's hide step, so `HideKeepsClaude` and `HideNoError` cover it through the same guards. It adopts nothing itself: `diff.lua` calls `get_active_terminal_bufnr` first, which adopts after a reload. No fact reads that adoption: `M.get_active_bufnr` of both providers is hashed (`native_active`, `snacks_active`), so a change reads STALE, and the model has no step for it, because none of the eight rules depends on which entry adopts first. If a change drops it, a Snacks float stays over a diff after a reload, and callers see no active Claude. A hide through it keeps the job, and nothing shows the float again but the user's toggle.
- Snacks keys an instance by its command, directory, env and count, and clears the key when a buffer is wiped, whichever instance holds it, so `Snacks.terminal.list()` can lose a running Claude. The code finds its Claude by the mark and a live job instead, so the model needs no key. `snacks-reload-exit.lua` replays the path (both orders of a `TermClose` autocmd and the provider's handler), and `snacks-exit-handlers.lua` replays the two ways that wiping early goes wrong (a wipe inside `TermClose` deletes the autocmds that remain for that event; an exit before the first entry after a reload).
- A snacks start writes up to four buffer variables: the mark `b:claudecode_snacks_terminal`, `b:claudecode_snacks_auto_close`, `b:claudecode_snacks_window` (the resolved window options as plain data) and, for a float with a backdrop, `b:claudecode_snacks_backdrop` (the backdrop's window id). An adoption wraps the buffer in a new Snacks window built from them (`Snacks.win` with `buf`, in the `terminal` style), maps the wrapper's own keys over those of the first start (the entry's config gives the user's keys, functions included), and tracks the window of the current tab that shows the buffer, as the instance that the provider started tracks the window that it showed. The provider writes the backdrop variable again each time Snacks re-creates a float. The model sees the mark (a terminal is live when it carries it). The other variables, the keys and the window tracking decide what an adopted terminal looks and acts like, which no rule checks, and the replays `snacks-reload-adopted.lua`, `snacks-reload-keys.lua`, `snacks-reload-tabs.lua`, `snacks-reload-backdrop.lua` and `snacks-reload-older.lua` replay them. A terminal that an older version started has no variable, so the entry's config decides, and an entry without a config (`get_active_bufnr`, `close`) wraps it first and maps no key, and the first entry that brings a config maps the keys (`upgrade_wrapper`).
- The model keeps scheduled callbacks as a set, not in order. A path that needs a particular order of two plugin callbacks must be replayed before you trust it.
- `focus_toggle` is modeled as hide or focus when Claude is visible, because the model has no keyboard focus. It covers `simple_toggle`. `ensure_visible` is modeled as an open.
- Windows are modeled only as far as the rules need: whether Claude's window is open, whether it is the last window, and whether native's tracked window shows another buffer. Snacks windows are splits. Snacks floats (config-hidden on hide), tab pages, and window sizes are not modeled. Snacks' `fixbuf` is assumed, so `:e` in a snacks window is not a step.
- After the reload, the old module copy's window is tracked only while it still shows its terminal. The old copy's view of a window that you switched to another buffer is not modeled. A terminal adopted after the reload keeps the module copy that started it (`old`). Native adds a handler on adoption (`NativeAdoptedExitHandled`) that reaches the new copy's state. Snacks adds none: its entries forget an exited terminal instead (`SnacksEntriesForgetEndedJob`).
- These are not modeled. Each line says what you would see if it broke, as far as the checks that exist tell:
  - The `external`, `none` and custom table providers: Claude opens in the wrong external command, an integrated terminal opens when none should, or your own functions are called wrongly. `terminal/external_spec.lua`, `none_provider_spec.lua` and `terminal_spec.lua` test them.
  - A close that starts during another close's wait: a reentrant close targets the wrong job or returns early. No failure is known.
  - A start-time autocmd beyond one open or one toggle per start (the model runs one call per start): a `BufEnter` or `TermOpen` autocmd that calls `focus_toggle` hides the new split, a second `simple_toggle` does the same, and a `:close` of the split closes it. The model reaches the same state through its hide step. Before #527 the start then raised `Invalid window id` at `native.lua:263` and Claude ran with no window. `native-start-autocmd-hide.lua` runs all three forms, and a hide followed by a show in another window, on real Neovim (the model has no window ids).
  - A `WinNew` or `WinEnter` autocmd that calls an entry while native's `vsplit` runs, before the new buffer has its mark: native starts two Claudes, and a close returns with one still running. The model has no step before the split exists. #544 fixes it.
  - Which window the plugin made. The model's Claude window is any window that shows the terminal buffer. It does not say that the plugin made it. When native recovers a window of yours that shows the terminal (a `:sbuffer` of yours, found by `is_valid`), an exit with `auto_close` closes that window, and `ExitClosesOnlyOwnWindow` cannot tell. `AGENTS.md` (Code Shape) asks a cleanup to close only a window that the plugin can show it made. The model does not check that the code keeps to it.
  - A cleanup that raises. The facts read the order of the calls in the code, not that every call completes. `NativeFailCleansUp` reads `nvim_win_close(new_winid, true)`, the buffer delete and `cleanup_state()` in order, and the model takes the clean branch. When an autocmd has closed every other window, that close raises `E444`, and the buffer and the tracked state stay behind. The exit cleanup and the hide have the same limit.
  - A `TermClose` autocmd of your own that closes or deletes the terminal: the cleanup finds a deleted buffer or job. `native_terminal_toggle_spec.lua` and `snacks-exit-handlers.lua` test the orders.
  - `send_to_terminal`: text goes to the wrong job, is lost, or is sent wrongly. `send_text_spec.lua` tests it.
  - `paste_fix`: a streamed paste is duplicated, split or joined wrongly. `paste_fix_spec.lua` tests it.
  - The `<C-z>` mapping (`utils.map_terminal_suspend`): `<C-z>` reaches Claude instead of suspending Neovim, or overwrites your own key. `utils_spec.lua` tests it.
  - A second reload: adoption starts duplicate jobs, leaves old callbacks, or uses stale wrappers. The reload tests include repeated reloads.
  - The Neovim hang that the 1 s wait in close works around (neovim/neovim#42508): Neovim hangs when a close deletes a buffer whose write has not drained. The code documents the limit, and no test covers a job that stopped reading.
  - `:bdelete`: deleting the terminal buffer ends or hides Claude, and a later entry starts or adopts one. The model's wipe step is the nearest case.
  - `:q` in Claude's window: the window closes and Claude keeps or loses its job, depending on `bufhidden` and the last-window rule. The hide tests cover the exercised cases.
  - Neovim exit: cleanup hangs or leaves a process. The replays stop their jobs themselves.
